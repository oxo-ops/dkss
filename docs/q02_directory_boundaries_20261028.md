# Q02 候補検索APIの会社と権限の境界

## 対象と選定

承認先と通知先を選ぶ3つのAPIを実Flask要求で検証する。
`/api/approval-candidates`、`/api/mention-users`、`/api/news-targets` が対象。
既存Q02は通知レコードの本人境界と承認操作の権限を検証しているが、これら候補検索APIの会社・営業所・役割の切替は直接検証していなかった。
APIに表示される候補は承認操作の許可そのものではない。登録・承認時の再判定は既存の別試験で扱う。

## 追加7件

| 条件 | 期待結果 |
| --- | --- |
| 一般利用者のCookieで役割と営業所を偽装し、クエリに他社コードを指定 | DBの現会社・現営業所の管理者だけを承認候補として返す |
| 営業所異動と所属解除の後に旧営業所のCookie・クエリを再送 | 新営業所の候補へ切替。所属未設定なら空一覧 |
| 表示中の承認候補を一般利用者へ降格 | 再取得で候補から除外。他社の同名管理者で補完しない |
| 両社の同名ITC利用者で会社・営業所・利用者の通知先検索 | それぞれ認証中の会社だけを返す。他社固有語の検索は空一覧 |
| ITCから管理者へ降格後に旧ITC Cookieを再送 | 通知先の3種類の検索すべて403。空のresults |
| メンションの完全一致と承認用の役割フィルター | 会社をまたがず、adminとadmin_userの指定どおりに候補を限定 |
| ロック後、APIごとに旧ITC Cookieを戻して取得 | 3 APIとも401。セッション失効、個人候補を返さない |

利用者・会社・営業所・マニュアル・通知の全列を前後で比較し、検索で業務データを更新しないことも確認する。
同名利用者と同名営業所を両社に用意し、許可側が空一覧のまま拒否だけ通る試験を避ける。
候補利用者のロック時に一覧から除く仕様は今回追加していない。
