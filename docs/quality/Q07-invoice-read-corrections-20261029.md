# Q07 M07 請求書単位の読取訂正

## 対象と期待結果

追加請求反映後の整備合計を原本と対応付けずに上書きすると、費用反映履歴と合計が不一致になり、後続の請求差替えが保護的に停止していた。

既存の整備編集画面で対象請求書と原本を選び、その請求書の読取額を訂正する。手入力分と有効な請求書の確認額から整備合計を自動再計算する。整備完了の再操作、再アップロード、合計の二重入力は不要。

* 元請求100＋追加30の場合、元請求を110に訂正すると合計140。追加30を新請求20へ差し替えると合計130。
* 同じ出発点で追加請求を40に訂正すると合計140。その追加請求を20へ差し替えると合計120。
* 手入力費用は請求書分を除いた値として編集可能。従来の負数・不明値の意味と整備状態を保持し、請求書の非負・合計必須チェックを手入力分へ広げない。独立した値引き・調整機能は追加しない。
* 過去に直接140へ訂正した記録は、差額10を推測配賦しない。既存画面で対象原本・保存済み読取値・現在の確認額を提示し、対象と訂正額の根拠を明示的に確認した場合だけ解決する。根拠不足・参照欠損・原本不一致の場合は140を保持し、差替えを拒否する。

## 保存・互換性

DBテーブル・列・型・制約は変更しない。移行処理、既存データの一括更新は行わない。既存の `VehicleMaintenanceRecord.invoice_details_json` に `invoice_cost_reads`（version 1）を追記する。

各sourceには既存の取込元ID・明細番号・SHA256・既存文書ID（存在する場合のみ）、保存済み読取値、訂正開始時の確認値、訂正履歴を保持する。履歴には訂正前後の5金額、整備合計の前後、旧不一致の解決有無、根拠確認、操作者UUID・username・UTC日時を追記する。既存の整備変更イベントにも対象原本と訂正前後を残す。

元請求の直接取込型は `invoice_details_json.source` と既存Draftの登録結果を照合する。存在しない `VehicleMaintenanceDocument` は作らない。Draftの保存済みpreviewは登録確認値を含む場合があり、失われた過去の抽出値を復元したことにはしない。原本bytes、Draft preview/result、文書payload、元の費用反映decisionは書き換えない。

履歴のない従来データも既存の費用反映履歴と実在する原本から読み取る。追加キーがない状態を既定形式として扱い、未知形式・不整合は拒否する。NULLは不明、0は既知のゼロとして区別する。差替え済み請求の訂正履歴は保持し、合計には有効な請求だけを算入する。

旧コードは新しい請求別訂正履歴を参照しないため、訂正開始後に旧コードへ戻して費用を書き込む運用は互換ではない。切戻し判断時は対象への費用書込みを止め、既存の移行・切戻し主管へ判断を引き継ぐ。本変更では運用・移行を実行しない。

## 原子性・境界・応答

既存の会社スコープ・権限・record_version・レビュー時の期待合計・再送拒否を維持する。請求別版には有効な文書と原本参照も含む。金額が同じ別文書への差替えも旧画面として拒否できる。

編集POSTも会社→記録→文書の順で取得し、レビューが使う会社の外側ロックと順序を合わせる。訂正・集計・変更イベントは既存トランザクション内で保存する。commit失敗時は全てrollbackし、再試行可能。GETでは原本BLOBを一括読込せず、金額変更時にbytesのSHA256を検証する。

既存の入力不足・完了操作拒否は400、版・出典・金額整合性の拒否は409、正常保存は既存の302を維持する。M07のHTMLエラー応答は提出値・対象原本選択を保持し、既存の復帰応答ヘッダーで共通リダイレクトによる値の喪失を防ぐ。共通HTTP例外処理、OCRログ、本人識別コードは変更しない。

## 検証と残る運用条件

修正前のmain `bb478c9` に新受入の初期8ケースのみを移して実行し、8件失敗を再現した。修正後は14ケース（元請求/追加請求、initial_cost型、曖昧な140、出典不足、原本不一致、手入力・負数・不明、旧版・他出典・再送、NULL/0、commit失敗、HTML復帰）をSQLiteと隔離PGで実行する。PGでは実際の2接続のロック待機も両順序で検証する。

従来の「混合合計140へ直接POSTできる」試験は承認された仕様により新規POSTを409とする。過去の140はfixtureで既存状態として作り、元の差替え拒否の検証を維持する。保護条件を緩和しない。

ブラウザは新規SQLite・架空原本・模擬OCR・loopbackだけを使う。PCの元請求訂正→差替え、スマートフォンの追加請求訂正と入力エラー復帰、過去140の明示解決、手入力の負数・不明→再確認→差替えを実施。実端末・実OCR・本番受入の完了とは扱わない。実行ログと画面証跡は作業フォルダーのoutputsに保全し、最終件数はPRのCI結果と合わせて報告する。

実装・SQLite/PG/ブラウザ・CI・PRまでの見積りは18〜30人時。旧140の根拠が不足する案件は件数・原本確認担当の判断待ちであり、推測補正しない。実データ確認・本番適用・移行・切戻しは本担当の実施範囲外。
