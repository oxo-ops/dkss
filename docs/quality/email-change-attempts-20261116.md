# メール変更コードのサーバー側試行上限（非本番）

Word v16 33.1 / 35.4 の認証・本人変更の残条件。main 18c7364 にて、
確認コードの5回失効は署名Cookieの email_change_attempts のみを信頼していた。
コード発行後のCookieを6クライアントへ複製し、異なる5クライアントで誤入力しても
サーバーのコードが残ることを一時SQLiteで再現した。本番被害の証拠ではない。

既存MFAと同様、コードのsalt付きハッシュからSHA-256識別値を作り、既存AuditLogの
会社・利用者・用途・識別値別の失敗数を正とする。コード/ハッシュ原文/変更先アドレスは
新しい監査detailへ記録しない。Cookie回数は表示用のみ。5回目の記録と無効化は同一commit。
PostgreSQLでは確認POSTと通知設定POST（発行側）でUser行をロックし、最新値を再読込する。
GETや他の設定操作にロックを追加しない。既存IP rate limitやCSRFは維持。

schema変更・移行なし。既存AuditLogを再利用するため、コード有効期間中（10分）の
失敗記録を削除しない運用が必要。既存未失効コードはそのまま使用できるが、配備前の
Cookieだけに残った失敗は永続履歴へ復元できず、配備後の失敗から数える。全callerを
同版に揃える必要があり、旧版が混在すればサーバー側制限を保証できない。

再発行の別saltハッシュは別の試行枠。本人確認前の宛先変更、メール送信の回数や
再試行、成功/期限切れ消去、通知設定の配送失敗rollbackは維持する。
DBの既存行やメールアドレスを移行しない。MFA本番有効化、共有端末機能、警告原因や
実配送の受入を完了とはしない。設定変更・実送信・本番アクセスなし。

一時SQLiteの7件（実設定POSTの再発行と配送失敗rollbackを含む）で複製Cookie/再発行/期限切れ/1回消費/会社分離/監査非露出と既存MFA・SMTPを検証。
PostgreSQL実競合は専用の使い捨てCIで確認する（ローカルPG未実施）。5回までの並列失敗、
4回後の2並列、同じ正解の8並列消費を対象にし、2以上の実backend接続を必須とする。

ローカル結果：最初の6件＋既存MFA15件＋SMTP5件は26成功12.575秒。
実設定POSTの1件追加後、新規7件を再検証し4.343秒で成功。全体CI・PGは未実施。

独立レビュー：5f89d45 の静的阻害なし、関連27件成功。後続で発行対検証の
PG競合1件を追加。模擬SMTPで発行を保持し、別backendの検証FOR UPDATEが待機すること、
解放後は新コードへ失敗1回を計上し新コードだけ消費できることを確認する計画。
実SMTP待機中は行ロックを保持するため、通知設定/確認要求の待ちが延びる可能性あり。
これは既存同期配送を非同期化する変更ではない。実PG4件と全CIは未実施。
