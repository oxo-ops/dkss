# Q11 復旧検証の自動化

最終検証の基準mainは `6c13df3859b0c6b7e2c35bfe360f4a15ff7bc85e`（PR #275まで）。前回の `6d7d8c9` からQ02・Q07の更新を確認し、重複がないことを確認して取り込んだ。2026年10月28日JSTに、WindowsとPostgreSQL 18.6、Python 3.12.14で架空データのみを使ったローカル検証を実施した。製品の復旧ロジック・データ定義・業務仕様は変更していない。

前回の資材はリポジトリ外の調査成果物だった。原本共有、SHA-256検査、旧カラム復元、OCRリース管理はmainに存在するため、それらの再実装は行わない。前回未実行だったseedはUserの必須 `last_name` が不足していた。本ツールは実際の必須列を満たすfixtureを生成し、既存の復旧関数を呼ぶ。

## 自動実行した異常ケース

各DB障害は同じ凍結dumpから作った別の空DBで実施する。期待した拒否を検出した場合はケースをpassedとし、証跡に `expected_rejection: true` を残す。失敗した復元を正常復元として数えない。

| 注入した異常 | 実際の合格条件 |
| --- | --- |
| ファイル欠損、同サイズ1バイト改変 | 元manifestの再生成なしに1件だけ失敗、残り3件は一致 |
| DB参照のあるmanifest項目を削除 | DB→ファイル参照1件の欠損を検出 |
| 共有原本の削除 | A社の有効参照3件の欠損を検出 |
| 共有原本の改変 | 共有ハッシュ1件とB社の有効参照2件の不一致を検出 |
| 整備知識原本の改変 | 知識原本のハッシュ1件の不一致を検出 |
| 整備記録を別会社へ付替え | 車両との会社不一致1件を検出 |
| FKトリガーをfixture内だけ無効化して孤児を作成 | 外部キー違反1件を検出 |
| マニュアル1行を削除 | 件数差1と内容ハッシュ差を検出 |
| CHECKの許容値を変更 | 正規化後も制約差を検出 |
| varcharの長さ200→201、sequenceの値とis_calledを変更 | 列定義差とsequence差をそれぞれ検出 |
| dumpを半分で切断 | pg_restoreが非ゼロ、不完全な復元先のpublicテーブル0、元DB差分0 |

PostgreSQL 18.6はdump/restoreの際、同じCHECK制約の `varchar[]::text[]` を各要素のtext変換へ書き直す。そのため両側のCHECK定義を同じPostgreSQLパーサで一時テーブルへ再パースして比較する。元の定義もJSONに残す。文字列の正規表現置換や制約差の無視は行わず、許容値を実際に変えたケースでは差を検出する。比較用の一時テーブルを除き、元DBには書き込まない。

## 再現方法

アプリのrequirementsと、initdb・pg_ctl・createdb・pg_dump・pg_restoreが同じディレクトリにあるPostgreSQLが必要。WindowsとLinuxのコマンド例は次のとおり。既存サーバーのURLや認証情報を渡す引数はない。

```powershell
# リポジトリのルートで、依存導入済みPythonを使用する。
python tools/q11_recovery.py --pg-bin 'C:/Program Files/PostgreSQL/18/bin' --work-dir work/q11-new-run
python -m unittest discover -s tests -p test_q11_recovery_tools.py -v
```

```bash
python tools/q11_recovery.py --pg-bin /usr/lib/postgresql/16/bin --work-dir /tmp/q11-new-run
python -m unittest discover -s tests -p test_q11_recovery_tools.py -v
```

work-dirは毎回新しい名前にする。既存ディレクトリは空でも拒否し、以前の証跡やクラスタは削除しない。PostgreSQLをrootで起動しない。ローカルの空き容量に余裕を持たせる。今回のWindows実行はPostgreSQL 18.6、CIではUbuntuのパッケージ版を使い、実際の版をJSONへ記録する。CIの実施状態はPRのチェック結果で別途確認する。

生成物は次のとおり。

- `report.json`：全体・各ケースの成功失敗、所要時間、件数、期待した拒否、原本の期待値と実測値。
- `commands.json` と `command-*.log`：dump/restore等の引数、終了コード、所要時間、標準出力・エラー。
- `before.json`、`after.json`：テーブル・sequence・定義の比較基準。
- `manifest.json`：復旧前のファイルサイズとSHA-256。原本は `files-source` と `files-restored`。
- `baseline.dump` と `truncated.dump`：架空DBの正常バックアップと障害注入用コピー。
- `postgres.log`、`pgdata`：検証専用クラスタ。終了時に停止し、削除しない。

コマンド成功は全ケース成功かつ停止処理成功の場合のみ終了0。途中で予期しない失敗があれば終了1とし、その先のケースは未実施と扱う。新規work-dirを作れない場合は実行前に拒否する。失敗の証跡を上書きするための同じディレクトリでの再実行はしない。

## 前回項目との対応と残る工数

前回T01の基本復元、T05の途中障害・再開、T06の行ロック、T09のキャッシュ分離はローカル架空fixtureで実施済み。T02はローカルファイルとDB参照まで、T03はdump切断まで、T04は現行コードのインライン復元まで、T07は復元されたリースと実DB停止まで、T11はデータの会社対応と新規採番まで実施した。T08・T10の実S3、T12の運用受入は完了していない。

| 残る作業 | 人時の見積もり |
| --- | --- |
| 検証専用アカウントのS3世代・削除マーカー・IAM・暗号鍵・署名URLとDBの復旧時点の受入。アクセス先確認・環境準備を含む | 5–8 |
| 旧版SHAの決定、旧版依存関係、切戻し後の実画面と新規登録、全添付種別の確認 | 3–5 |
| 実運用相当のPostgreSQLメジャー版・拡張・ACL等と、容量制限・権限不足・実容量での性能確認 | 2–4 |
| 実OCRワーカーのプロセス停止とネットワーク障害、実行中外部処理の重複リスクの確認。外部AIは模擬でよい | 1–2 |
| 復元サービスでの会社境界、権限失効、主要画面と業務上の参照の受入 | 2–3 |
| RPO/RTO、バックアップ世代の選び方、再開可否、証跡保存担当の決定と通し訓練 | 3–4 |
| 合計 | **16–26人時（2–3.25人日）** |

前回の36–56人時から、対応する端の比較で20–30人時を削減できる見込み。これは残作業の再見積もりであり、開発時間の実測による削減率ではない。検証専用基盤と架空の代表資料を準備でき、重大な新規不具合が見つからない前提。実運用容量の転送待ちや発見不具合の修正は別途。RPO/RTO値は未決定のため、ローカル試験が成功してもQ11全体を完了扱いにしない。
