# Q05 未来起算日の表示・残存検証（2026-10-28）

基準 main: `bb3a118`。既存 PR #277 / #284 の修正は再実装しない。
利用者の追加仕様により、未来起算日は事前登録を許可したまま、開始前は
「開始予定（YYYY/MM/DD）」、当日は0日、過去は従来の経過日数を表示する。
開始前はランキングから除外する。保存値、スキーマ、SQL、キャッシュは変更しない。

## 表示経路

| 経路 | 対応 |
| --- | --- |
| 乗務者一覧のPC表・モバイル詳細カード | `masters.driver_master` の共通表示値を変更。`driver_master.html` の2箇所で共有 |
| ダッシュボード個人カード（管理者・一般利用者） | 日数をNoneのまま保持し、予定ラベルを渡す。予定時は「日」単位を描画しない |
| 無事故ランキング | 東京業務日より未来の行を追加前に除外。取得SQL、並び替え、上位10件処理は維持 |
| 編集・辞書出力 | `vehicle_readers.driver_to_dict` は起算日原文を保持。数値日数の専用CSV/Excel/API出力は検索範囲に存在しない |

空欄・年月のみ・不正日付に日を推測補完しない。既存の不明日付表示と
365日単位の年表示は変更しない。旧値 `2028-2-29` は表示だけ正規化し保存値は維持する。

## テストと結果

- 修正前: 新規SQLite HTTP/Jinjaテスト5件、7つの失敗サブケースで仕様との差を再現。
- 修正後: 上記5件を含む関連31件が合格。従来ダッシュボードのコンテキスト比較も合格。
- 境界: 東京の年越し、月末、2028年うるう日、未来→当日→翌日。
  利用者時刻帯をHonoluluにしても東京業務日を使うことを確認。
- 専用ローカルPostgreSQL 18.6: 7件中6件合格、1件失敗。
  集計行作成済みの場合、8接続・16HTTP要求で表示、ランキング、他社分離、保存値保持が一致。
- 初回集計行なしの8並列要求では `company_usage_summary_company_code_key` の
  UNIQUE違反でHTTP500。`audit.update_company_usage_summary` の検索後INSERTの競合。
  同じテスト資材をmainの独立展開にも適用して同じDB例外を確認した。
  mainでは未来ラベル未対応のため表示アサーションも失敗するが、DB例外は独立してログに存在する。
  同時SELECT完了をバリアで揃えて再現を安定化している。失敗テストは削除・緩和しない。
  共通集計処理は他担当範囲なので修正せず、専用PostgreSQL CIでも未解決を可視化する。

実ブラウザ検証は未実施。Windows Computer Use が現在URLを確認できず、このターンの
操作を停止した。HTTP/Jinja試験はブラウザ自体の時刻帯変更・描画確認の代替とは扱わない。
このため、また上記同時アクセス不具合が残るため、PRはドラフトとする。

## Q01・過去日時との照合

追加のQ01成果は利用者から未提示。mainの仕様・保存定義を正として照合した。
Driver.safe_start_date は String(20) の日付原文であり時刻変換の対象ではない。
通知の文字列日時にはUTCを明示する新規値と、時刻帯のない旧値がある。
`notifications.format_notification_datetime` はaware値のみ利用者時刻帯へ変換し、
naive値のソートでは現在の利用者時刻帯を使う。
`checklist_common.get_user_local_now` は利用者設定の時刻帯、失敗時は東京を使う。
DB列には文字列と timezone=True の日時が混在するため、9時間差だけから旧値の保存基準は確定できない。
原文・保存形式・既存変換処理を維持し、一括変換はしない。

Q01との厳密な差分照合には、旧値の作成元・当時のサーバー時刻帯・当時の利用者時刻帯が必要。
今回の仕様差分は「未来は従来表示のまま」という以前の調査前提を、利用者が承認した
開始予定表示・ランキング対象外に更新する点のみ。
