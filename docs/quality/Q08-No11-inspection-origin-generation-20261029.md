# Q08 No.11 点検起点・車両候補訂正の人物世代

調査開始はmain `0832720`（Q03 #283 / Q08 #297 統合済み）、PR作成前に最新main `40ac8ac`へ追従した。No.11だけを変更し、#297の通知・日報権限・リマインダー・旧Cookie対策は再実装しない。

## 再現と制約の区別

架空のAが日常点検を入力 → Aを物理削除 → 同username・同数値User.id、異なるaccount_identityのBを登録した。SQLiteは全試験用接続でFKを有効化、PostgreSQLは既存FKを維持した。数値IDの明示再利用は復元・取込などの条件を模し、PostgreSQL通常シーケンスが必ず再利用するという主張ではない。

訂正前でUserを参照する訂正FKが存在しない場合、両DBで削除が成功し、BのHTTP GETにAの候補（日付・車両・点検ID）が表示され、旧フォームPOSTも302で訂正を追加した。修正前の否定試験は両DB各3件（候補非継承、旧フォーム拒否、起点UUID保存）が失敗した。

訂正済みの場合、対象者user_idまたは操作者actor_user_idのFKにより物理削除は拒否された。対象・操作者をそれぞれ検証し、この制約や一意制約を緩めて再現していない。過去のNULL世代・不一致世代の訂正は、現在のFKを満たす架空の旧形式記録として別に検証した。現行制約下で禁止される削除が成功したとは扱わない。

PostgreSQLでは、起点の日時がマイクロ秒＋時差で32文字となり、既存VARCHAR(30)へ保存できない問題も確認した。修正前の人物境界再現には秒精度の架空の旧日時を使用。製品側は時差を保ったミリ秒精度29文字に収め、既存列を拡張しない。最終試験は日時のモックなしで新規入力を検証する。

| 訂正対象者 | DrivingVehicleCorrection.user_id | 数値FKを保持しuser_identityを追記。旧世代を適用・表示しない |

| 訂正確認者 | 独立した承認者は存在しない | 本人訂正または管理者による対象者訂正という既存仕様を維持。新たな承認段階は追加しない |

管理者の会社閲覧や数値フォーカスキー自体は新たな個人権限を与えない。起点UUIDの照合と、一般利用者は自分の対象だけ保存できる確認を追加した。従来のevidence_keyの算出対象・意味、元点検の回答・車両・添付、運転日報の原本は変更しない。

## 旧データの扱い

| 架空の記録 | 処理 | 復旧に必要な証拠 |
| --- | --- | --- |
| 起点UUIDが現本人と一致、新訂正の対象/操作者UUIDあり | 候補表示・訂正・履歴を通常通り使用 | 追加確認不要 |
| 起点UUIDなし（現在の点検確認者UUIDはある） | 候補として自動表示しない。起点は保持 | 入力開始時の本人を示す独立した証拠。後の確認者は同一とは限らない |
| 起点UUIDが別人 | 表示・旧フォームPOSTを拒否。旧起点を保持 | 別人Bへの復旧対象ではない |
| 数値IDだけの旧訂正、操作者UUIDなし、対象UUID不一致 | 該当点検の候補・訂正履歴を保留、適用しない。行・revisionは保持 | 起点・訂正対象・実操作者の同一性を独立確認 |
| 同UUIDの改姓・ロック解除 | 正常利用を再開し、旧氏名の証跡は保持 | 通常の認証・ロック解除。物理削除後の新UUIDとは別扱い |

旧訂正がある点検は、evidence_keyが変わっていても未同定revisionが残る間は保留し、既存数値キーのrevision一意制約との衝突や旧履歴の引継ぎを防ぐ。UUID不明の旧訂正を本人集計へ自動適用しなくなるため、以前の訂正による個人集計保留は再評価され得る。原本値を補正する変更ではないが、適用前に旧訂正件数と表示影響を隔離検証し、仕様責任者が復旧対象を判断する必要がある。本人確認付きの復旧・取消機能は未実装で、username・氏名・現在の数値IDからのバックフィルは禁止する。

## SQLite / PostgreSQLの移行・切戻し手順案

本番では未実施。既存Q03移行済みmainが前提。実施者は通常のバックアップ・停止手順に従う。

1. 書込みプロセスとワーカーを停止し、DBをバックアップ。Q03の既存人物UUID列・User.account_identityを確認する。過去の起点や訂正を現在のUserへ対応付けるSQLを実行しない。
2. 本PRのコードで `flask --app app init-driving-access` を明示実行する。既存訂正表にはnullableのuser_identity / actor_identity / actor_nameだけをALTER ADD COLUMNする。既存FK・一意性・revision・行の値は変更しない。新DBは既存create処理で作成する。
3. 同コマンドを再実行し、列重複・データ更新がないこと、FKと一意制約を確認。PostgreSQLは既存初期化のトランザクション/アドバイザリーロック内で実行。SQLiteは書込み停止下で実行する。
4. 起点UUIDあり/なし・旧訂正・新規訂正・別会社・再登録を隔離環境で確認後、通常の承認手順で稼働を再開する。GET・factoryはDDLを実行せず、訂正の列が不足する場合は保存503として拒否する。
5. 切戻しは新しいnullable列と証跡を残す。再度書込みを停止し、UUID照合を保つ既知の修正版へ戻す。数値IDだけを信頼する旧コードへの復帰や列削除は、この漏えいを再導入するため安全な切戻しではない。対応版が用意できない場合は候補訂正を停止したままにする。バックアップ復元が必要な場合は、その後の追記証跡を別途保存・照合してから判断する。

受入試験では旧形式表を新規に作り、元のFK・一意制約を保持したままNULL列の追加、Q03移行→本移行→Q03再実行→本移行再実行を両DBで確認する。移行前の読取りでDDLが発生しないこと、移行未完了時の保存拒否も含む。破壊的な逆移行は実装・実行していない。

## 添付とNo.10の留保

車両点検添付はstorage.pyの現行実装で会社単位の共有。架空ファイルを作り、Aと無関係な同社一般利用者Cが削除前から読めること、再登録BもHTTP200で読めること、他社は404となることを確認した。これはNo.11の数値IDによる個人権限継承とは別経路で、候補の遮断だけで添付を個人限定にできたとは報告しない。個人情報を含む添付の共有仕様はQ03・仕様責任者へ確認事項として引き継いだ。添付・storageの製品コードは変更していない。

No.10（未紐付け旧日報の氏名自動照合による別人閲覧）は未解決P1を維持。運転分析担当「運転分析機能を改善」へ、現行仕様・閲覧条件・管理者の明示再承認方式の判断が必要と伝達済み。同担当はNo.10を調査中で、今回Q08は氏名照合、一覧・詳細・CSV/PDF・AIの閲覧条件を変更しない。Q02 OCR所有者、Q03フォーム競合、Q04マスタID再利用のコードにも触れていない。
