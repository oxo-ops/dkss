# U32 maintenance corrections and generated part history

Baseline: `0432cfc9d4ba2455a8143353804897b41b9a090a` (main, 2026-10-30).

The U32 audit described stale part dates/mileage after maintenance correction
(specification v0.25 Q08-reflected edition, chapter 06 p20 and chapter 18 U32
p56, as referenced by the audit handoff). Existing production code already
checks source line index, replacement action, line hash, company/vehicle/parent
ownership and old-value equality before propagating corrections. The old
overview test only exercised a direct parent mutation with no source; it did
not establish the HTTP save contract.

## Result and scope

No product defect reproduced on the baseline in the covered sequential HTTP
flows. This change adds regression evidence; it does not modify application
behavior, schemas, production data, or the formal Word originals.

`tests/test_u32_part_sync.py` creates synthetic PDF bytes and uses the real
upload, confirmation and maintenance-edit endpoints. Only OCR is mocked.
Parts and source links are generated by application code rather than seeded
to make a positive synchronization test pass. The fixture creates a disposable
SQLite database and disables external services.
It supplies an authenticated administrator session and disables CSRF in the U32
fixture. The separately run Q02 auth/CSRF suite covers login/MFA; its success is
not direct CSRF acceptance evidence for the maintenance-correction POST route.

Covered contracts:

- Imported part mileage/completion date follow the correction, and both parent
  and part changes are recorded in the maintenance audit event.
- Entry date is used when completion date is absent; completion date takes
  precedence, including when set or cleared in later corrections.
- Independently measured mileage/date are retained field by field.
- Clearing mileage preserves unknown, and later correction propagates again.
- Missing source, invalid index, mismatched line hash, non-replacement action,
  foreign source and foreign part do not authorize propagation.
- Hand-entered maintenance can be corrected without inventing parts/sources.
- Stale form submissions do not create a second correction or event.
- Forced commit failure rolls back parent, part and event together; retry works.
- Original PDF bytes/hash, extraction preview, line items and source version
  remain unchanged after correction.

Malformed-source cases deliberately alter synthetic fixture rows only. They
test defensive filtering, not permission to repair real historical data.

## Validation

Run from the repository root with `PYTHONPATH=.:tests` on Linux or `.;tests`
on Windows, with `AWS_EC2_METADATA_DISABLED=true`:

```text
python -m unittest test_u32_part_sync test_document_connections test_vehicle_overview test_q02_vehicle_boundaries test_q02_auth_csrf -v
```

The existing Regression Tests workflow discovers the new tests automatically;
no additional workflow or repeated unrelated baseline campaign is required.

Local result (Windows, Python 3.14, 2026-10-30): **105 passed** in 134.423s.
This includes the overview module's imported workflow fixture cases. After
making event ordering deterministic and reloading original rows for assertions,
the final U32 class was rerun: **12 passed** in 19.140s. Deliberately injected
commit exceptions are expected rollback-test output. Existing tempfile resource
warnings did not fail the related suite. CI provides the repository's Python
3.12 check on the PR head.

## Remaining acceptance limits

This evidence covers sequential application saves on synthetic SQLite data.
It does not certify PostgreSQL locking/concurrent correction, live data quality,
browser behavior, or production deployment. Existing independent values that
happen to equal the parent's old value cannot be distinguished by a new policy
in this test-only change. Historical inconsistent sources stay protected;
repairing real records would require separately approved investigation and
data changes. Merge and deployment remain approval-gated.
