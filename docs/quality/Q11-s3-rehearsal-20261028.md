# Q11 検証専用S3の復旧リハーサル

この手順は、承認済みの検証専用AWSアカウント・バケットに作る架空資料だけを対象とする。今回AWSへは接続していない。アカウント、ロール、バケット、リージョン、キーの範囲、暗号化条件が未提供のため、下記は未実施の手順案である。既存PR #278のローカル原本照合を再実装しない。

## 実施前に受け取る情報

| 必須情報 | 確認する人と停止条件 |
| --- | --- |
| 検証専用account ID、承認されたcaller ARN、region、認証profile、短期認証の期限 | 環境管理者。productionとの共用アカウントや共用ロールでは実施しない。秘密鍵・アクセストークンは資料やチャットに転記しない |
| source/restore bucket名とowner ID、今回だけのprefix、run ID | 環境管理者。復元先はsourceと別バケット。名前から検証用と推測しない |
| Versioning、Lifecycle、Object Lock、MFA Delete、Public Access Block、Object Ownership | 環境管理者が設定値を提出。試験途中で有効な世代が消える保持設定なら延期する。既存設定の変更はこの手順に含めない |
| writer、restore、A社reader、B社reader、deny-testの専用ロール | IAM担当。resource・prefix・bucket owner・必要時のKMS keyを限定。SCP、permission boundary、session policy、VPC endpoint policyの制約も確認 |
| SSE-S3かSSE-KMSか、検証専用KMS key ARNとkey policy、必要な暗号化context | 暗号鍵管理者。SSE-KMSの情報がなければKMS試験は未実施とする |
| 復旧基準時刻、許容する資料欠損、DBとmanifestを凍結する担当、記録の保管先 | 業務責任者と復旧担当。RPO/RTOの承認がなければ全体受入を保留 |

PR #278のローカル保存域はAWSのIAM・世代・暗号鍵の挙動を証明しない。一般用途バケットを対象とし、directory bucket等の別仕様は環境管理者が対象に含めると決めるまで扱わない。

## IAMの確認表

IAMポリシーはここで自動適用しない。管理者が下記の正負ケースを満たす専用ロールを準備し、承認済みのResource ARNを記録する。GetObjectとVersionId指定取得は必要なactionが異なる。[AWSのAPIと権限の対応](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html)

| 操作 | 必要な権限の候補と範囲 | 負の確認 |
| --- | --- | --- |
| 設定採取 | 対象bucketのGetBucketVersioning、GetEncryptionConfiguration、必要な設定参照。IAM担当が正確なaction名を確定 | 他bucketの参照を拒否 |
| 世代一覧 | source bucket ARNの `s3:ListBucketVersions`、承認prefixのみ | prefix外の一覧を拒否 |
| 現在物の読取 | 対象object ARNの `s3:GetObject` | A社readerからB社キー、B社からA社キーを拒否 |
| 特定世代の読取 | 対象object ARNの `s3:GetObjectVersion` | GetObjectVersionを持たない別ロールでVersionId指定取得を拒否 |
| 架空原本の作成と復元 | writerはsourceの試験キー、restoreはrestore bucketの試験キーへの `s3:PutObject` | restoreがsourceを上書きできないことを確認 |
| 削除マーカー生成 | writerにsourceの試験キーだけ `s3:DeleteObject` | `s3:DeleteObjectVersion`を復旧ロールへ一律付与しない |
| SSE-KMS | 対象keyの `kms:GenerateDataKey` と読取に必要な `kms:Decrypt`。key policy側の許可も確認 | S3読取許可があるがKMS復号許可がない専用ロールで失敗を確認 |
| 片付け | 別のcleanupロール、今回作成したVersionIdとmarkerだけ | バケット全削除・prefix全削除は実施しない |

実効権限はidentity policyだけで決まらない。bucket/key policy、SCP等の明示denyを含めて確認する。SSE-KMSの権限と同一regionのkey等の条件は [AWSのSSE-KMS説明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html)を基準にする。アプリは現在 `dkss_app/storage.py:208–212` でAES256を明示している。KMSを必須化した検証は別のCLI fixtureで行い、アプリの暗号化仕様を無断変更しない。

## 接続先の確認

LinuxのBash例。値は環境管理者から受領し、既定のprofileや本番設定へフォールバックさせない。この例は両bucketのownerが同じ検証専用accountであると管理者が確認した場合に限定する。ownerが異なる場合は別の承認済み構成を準備し、同じ値を推測して流用しない。以下の変数が未設定なら実行は停止する。`Q11_PREFIX`は承認された今回専用の範囲で、末尾 `/` は付けない。コマンド例はすべて未実施。

```bash
set -euo pipefail
export AWS_EC2_METADATA_DISABLED=true
: "${Q11_PROFILE:?専用writer profileが必要}"
: "${Q11_REGION:?検証regionが必要}"
: "${Q11_ACCOUNT_ID:?承認済み検証account IDが必要}"
: "${Q11_BUCKET_OWNER:?承認済みbucket owner IDが必要}"
: "${Q11_SOURCE_BUCKET:?検証source bucketが必要}"
: "${Q11_RESTORE_BUCKET:?別の検証restore bucketが必要}"
: "${Q11_PREFIX:?承認された今回専用prefixが必要}"
test "$Q11_SOURCE_BUCKET" != "$Q11_RESTORE_BUCKET"
AWS=(aws --profile "$Q11_PROFILE" --region "$Q11_REGION")
account="$("${AWS[@]}" sts get-caller-identity --query Account --output text)"
test "$account" = "$Q11_ACCOUNT_ID"
"${AWS[@]}" sts get-caller-identity --query '{Account:Account,Arn:Arn}'
# 表示されたArnを承認されたprincipalと照合し、違う場合は停止する。
"${AWS[@]}" s3api get-bucket-versioning --bucket "$Q11_SOURCE_BUCKET" \
  --expected-bucket-owner "$Q11_BUCKET_OWNER" > source-versioning.json
test "$("${AWS[@]}" s3api get-bucket-versioning --bucket "$Q11_SOURCE_BUCKET" \
  --expected-bucket-owner "$Q11_BUCKET_OWNER" --query Status --output text)" = Enabled
"${AWS[@]}" s3api get-bucket-encryption --bucket "$Q11_SOURCE_BUCKET" \
  --expected-bucket-owner "$Q11_BUCKET_OWNER" > source-encryption.json
```

restore側もowner・設定・Versioningを同じ方法で採取する。403を「設定なし」と解釈しない。設定参照権限がない場合は管理者の設定記録を受け取る。環境確認後に各ロールでもSTS identityを照合してから、そのロールの正負試験へ進む。

## 世代と削除マーカーの試験

1. ローカルで異なる内容の架空v1/v2を作り、アップロード前にサイズとSHA-256を採取する。A社とB社のキーには異なる内容を使う。例の `q11-v1.txt` 等はこのための架空資料で、既存資料のコピーではない。
2. 同一キーへv1、v2をPUTし、それぞれのVersionIdとETag、SSE、ContentType、CacheControl、作成時刻を保存する。VersionIdがnullなら停止する。アプリの原本ハッシュの代わりにETagを使わない。

```bash
printf '%s\n' 'Q11 fictional original version 1' > q11-v1.txt
printf '%s\n' 'Q11 fictional original version 2' > q11-v2.txt
sha256sum q11-v1.txt q11-v2.txt > expected-sha256.txt
key="$Q11_PREFIX/uploads/Q11A/a.txt"
v1="$("${AWS[@]}" s3api put-object --bucket "$Q11_SOURCE_BUCKET" --key "$key" \
  --body q11-v1.txt --server-side-encryption AES256 --content-type text/plain \
  --cache-control no-store --expected-bucket-owner "$Q11_BUCKET_OWNER" --query VersionId --output text)"
v2="$("${AWS[@]}" s3api put-object --bucket "$Q11_SOURCE_BUCKET" --key "$key" \
  --body q11-v2.txt --server-side-encryption AES256 --content-type text/plain \
  --cache-control no-store --expected-bucket-owner "$Q11_BUCKET_OWNER" --query VersionId --output text)"
test -n "$v1"; test -n "$v2"
test "$v1" != None; test "$v1" != null
test "$v2" != None; test "$v2" != null; test "$v2" != "$v1"
"${AWS[@]}" s3api list-object-versions --bucket "$Q11_SOURCE_BUCKET" \
  --prefix "$Q11_PREFIX/" --expected-bucket-owner "$Q11_BUCKET_OWNER" > versions-before.json
```

3. writerでVersionIdを付けずに同じ試験キーをDELETEし、返却されたDeleteMarkerとmarkerのVersionIdを保存する。Versioning Enabledであることを再確認してから行う。これは全削除の手順ではない。
4. 現在物のGETが欠損扱いになること、marker自身のVersionIdをGETすると405になること、v1/v2のVersionIdを指定すれば元バイトが残ることを確認する。欠損時の403/404はListBucket権限の有無にも依存するため、ロールごとの期待値を記録する。[削除マーカー](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeleteMarker.html)、[GetObjectの応答と権限](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)
5. 復旧対象時点に対応するv1を読取専用restoreロールで取得する。ローカルの事前SHA-256と照合後、別restore bucketへ同じ試験キーでPUTする。元VersionIdと復元先の新VersionIdを対応表に残す。VersionIdの同一性を要求せず、原本バイト・metadata・所有/読取範囲の一致を要求する。

```bash
: "${Q11_RESTORE_PROFILE:?承認済みrestore profileが必要}"
AWS=(aws --profile "$Q11_RESTORE_PROFILE" --region "$Q11_REGION")
test "$("${AWS[@]}" sts get-caller-identity --query Account --output text)" = "$Q11_ACCOUNT_ID"
"${AWS[@]}" sts get-caller-identity --query '{Account:Account,Arn:Arn}'
# このArnも承認済みrestore principalと一致することを確認してから続ける。
"${AWS[@]}" s3api get-object --bucket "$Q11_SOURCE_BUCKET" --key "$key" \
  --version-id "$v1" --expected-bucket-owner "$Q11_BUCKET_OWNER" q11-restored-v1.txt > get-v1-metadata.json
cmp q11-v1.txt q11-restored-v1.txt
sha256sum q11-restored-v1.txt
"${AWS[@]}" s3api put-object --bucket "$Q11_RESTORE_BUCKET" --key "$key" \
  --body q11-restored-v1.txt --server-side-encryption AES256 --content-type text/plain \
  --cache-control no-store --expected-bucket-owner "$Q11_BUCKET_OWNER" > restore-version.json
```

6. v2を選んだ誤復旧、別会社のキー、存在しないVersionId、KMS拒否を別試験として実施する。DBとmanifestがv1を要求している場合に、v2を現在物として取得できただけでは合格にしない。

このprefix付きfixtureはS3 APIの検証用。アプリのキー生成には任意のprefix設定がないため、実画面の試験では専用bucketに既存形式の `uploads/Q11A/...`・`manuals/Q11A/...` 等を別途準備する。API用のprefix付きキーをそのままアプリで読めると仮定しない。

## 暗号化と署名URLの試験

暗号化はHeadObjectの実際のSSE・KMSKeyIdと読取結果を確認する。bucketのdefault設定だけで判定しない。SSE-S3の成功とは別に、SSE-KMSを運用する条件なら承認済みの専用keyを指定してv1/v2を作り、正しい読取ロールとDecryptを持たないロールで正負試験を行う。鍵の無効化や共用policyの書換えを障害注入として使わない。

署名URLは認証情報の一種として扱い、URL全文をログ・資料・チャットへ保存しない。boto3の `generate_presigned_url('get_object', Params={'Bucket': bucket, 'Key': key, 'VersionId': v1}, ExpiresIn=60)` で試験用VersionIdのURLをメモリ内に作り、直後にGETして返却バイトのSHA-256を照合する。保存するのは発行時刻・期限・HTTPコード・digestだけ。例外文字列にURLを含めない。

同じURLで期限経過後の新規GETが拒否されることを確認する。短期資格情報の期限やbucketのsignatureAge制約で早く失効する場合はその条件を記録する。署名生成自体は対象物へのアクセス成功を証明しないので、必ずGETまで行う。[署名URLの権限と期限](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

アプリの署名URLは現在VersionIdを指定せず、期限300秒で発行する（`dkss_app/storage.py:723–735`、`:774–784`）。直接S3の特定世代URL試験と、復元済みの現在物をアプリ経由で取得する試験を分ける。A社としてログインしたアプリからB社の原本を取得できないことも確認する。

## 合格条件と証跡

- bucket owner・caller・対象prefix・凍結時点の記録が揃う。
- 元manifestの会社・DB参照・キー・VersionIdで選択した全原本が一致し、余剰/不足と削除対象を説明できる。
- current/非current/markerを区別し、指定世代から別bucketへの復元が成功する。最新世代のsyncだけで代用しない。
- 許可するロールでは取得でき、他社・権限不足・期限切れのケースでは情報を返さない。権限を広げて負の試験を通さない。
- KMS利用条件が未確定、必要権限がない、基準時点が不明、digest不一致、説明不能な欠損のどれかがあれば再開判断を保留する。

今回の作成物のVersionIdとmarkerの一覧を保管する。cleanupは環境管理者が承認した担当へ引き継ぎ、無条件の再帰削除やバケット削除を行わない。
