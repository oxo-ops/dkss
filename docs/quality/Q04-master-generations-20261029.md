# Q04 マスタの世代識別と旧フォームの誤操作防止

## 原因と影響範囲

基点はmain `08327202afb1b6fa0b9960750cc289975c84e4e2`。#304のSQLite再現証跡を再確認した。5マスタの `_master_row()` は会社と数値IDで検索するだけだった。SQLiteのINTEGER PRIMARY KEYは最大ID削除後に同じIDを再利用するため、同名で再登録した別レコードが旧編集・削除フォームの対象になった。

営業所・車種・納入先・免許種別・内容区分の各編集/削除、計10件を実際の画面/ルートで固定し、修正前mainで10件すべての整合性アサーションが失敗、実行エラー0を確認した。単なる検出器の追加ではなく、保存処理を拒否する修正を行う。

営業所では新営業所の削除と車両・利用者・運転者の新割当解除、車種では新割当・取込対応の解除、免許では新しい免許JSONの書換えにつながる。納入先と内容区分にも旧フォームによる新レコードの編集/削除を確認した。履歴利用中の変更拒否など、従来の業務上の制約は維持する。

参照した仕様書v0.25のSHA-256は `d10255a317481e64654e37bd3e1f322a08cfad48b06ad6530a7b59955831b365` で、#304照合時から同じ。正本未確定という既存の文書管理方針を維持する。B0336の当時所属・Vehicle.id・他社非自動移管、B0414の復元/会社/権限照合と、今回の利用者指示を根拠とした。新しい業務仕様や移行承認を推定しない。

## 方式の比較と選定

| 方式 | 評価 |
| --- | --- |
| SQLite AUTOINCREMENT | 新規DBには有効でも、既存表への適用に再作成が必要。既存ID・参照・切戻しへの影響と破壊的変更の禁止から不採用 |
| IDと名称の署名/比較 | 同じID・同じ名称の別レコードを区別できないため不採用 |
| プロセス内の世代キャッシュ | 再起動・複数worker・復元で状態を共有/保持できず不採用 |
| 別の世代表 | 可能だが、全作成経路と二重の保存先を同期する仕組みが増える |
| **各マスタの不変世代＋署名フォーム＋SQL条件** | **採用。5列の追加で既存ID/名称/参照を保持し、同名・同IDでも別世代を識別する** |

5テーブルに `master_generation VARCHAR(36)` を追加する。新規ORMレコードは毎回新しいUUIDを取得し、同じレコードの名称変更では維持する。これはマスタのレコード世代であり、Q03/Q08の人物/アカウントUUIDとは別物で、その処理は変更しない。

編集画面・一覧の削除フォームに `master_token` を追加し、会社・マスタ種別・数値ID・世代・操作をアプリの既存SECRET_KEYと専用saltで署名する。CSRF・認可は従来どおり別に検査する。フォームの有効期限という新仕様は追加しない。

POSTは必要な物理列を確認し、会社内の対象を取得する。PostgreSQLではFOR UPDATE後に署名と世代を検証する。既存レコードの世代が不明、署名欠落/改変、会社・種別・ID・世代・操作の相違は409と再読み込み案内で拒否する。他社/存在しない対象への非開示のリダイレクトは維持し、保存しない。

SQLiteのFOR UPDATE無効を署名だけで補わない。SQLAlchemyのversion_id_colに世代列を指定し、通常更新では世代を変えず、**最終UPDATE/DELETEのWHEREにもIDと世代を含める**。検証後に別処理が削除・再登録しても、0行更新をStaleDataErrorとして検出し、関連行も含めてrollbackする。SQLiteのBUSY/LOCKED、PGの55P03/40P01/40001は既知の競合だけ409にし、自動再試行しない。未知の障害は500等の従来の失敗として残す。

## 明示的な既存DB移行

`tools/upgrade_master_generations.py` は初期化を呼ばない独立コマンド。専用環境変数 `Q04_MASTER_GENERATION_DATABASE_URL` と対象名・非本番確認が必須で、DATABASE_URLへフォールバックしない。PGはloopbackのQ04コピーのみ、SQLiteは明示した既存ファイルをmode=rwで開き、新しいDBを作らない。本作業では使い捨てfixture以外へ接続しない。

```bash
# 承認済みの非本番コピーを専用環境変数で選択し、全マスタ書込を停止する。
python tools/upgrade_master_generations.py --confirm-nonproduction \
  --expected-database dkss_q04_ci --schema public
python tools/upgrade_master_generations.py --confirm-nonproduction \
  --expected-database dkss_q04_ci --schema public --check
# SQLiteコピーの場合は同環境変数を明示して切替後に実行する。
python tools/upgrade_master_generations.py --confirm-nonproduction \
  --expected-database q04_generations.sqlite
```

5既存表を要求し、列がない場合だけADD COLUMNする。既存の有効な世代は維持し、未付与のNULLだけに初期世代を付ける。既存の不正値・重複世代は自動修復せず拒否する。ID、sequence、名称、会社、並び順、参照、人物UUID、請求/点検/通知/監査/履歴の値を変更しない。通常の起動・GET・POSTから移行や世代再発行を行わない。正常な削除監査のdetailには削除対象の世代を付け、同じ数値IDの新レコードへ旧削除記録を誤って対応させない。既存の監査行は書き換えない。

SQLiteはBEGIN IMMEDIATE、PGは5表へのACCESS EXCLUSIVEロックで移行を1トランザクションにする。PGのロック待機は2秒、各SQLは15秒で失敗し、途中の追加列/付与をまとめてrollbackする。カスタムtrigger/rule/RLS/継承等があれば、監査副作用や部分診断を避けるためDBA確認として停止し、勝手に無効化しない。失敗後の再実行で勝手に既存世代を振り直さない。

新規DBの列はNOT NULL。既存SQLite表は再作成せず追加列をnullableのままにし、NULL/不正値をreadinessと保存時に拒否する。旧バイナリや外部SQLによるNULL挿入を正常扱いにしない。`--check` は#304の読み取り専用接続を再利用するが、#304の診断コード自体は変更しない。初期化も既存表が未移行なら明示停止し、他の互換処理より前に管理者へ移行対象を示す。

## 導入と切戻しの条件

1. Q11の手順で一貫したバックアップ/復元コピーを作り、#304の5マスタ診断、owner/ACL、会社境界、件数・ハッシュ・添付を確認する。
2. **全旧web worker・CSV取込・管理書込を停止する。新旧バイナリのマスタ書込混在を許可しない。** 承認済みの別migration権限でコピーに移行を実行し、readiness、既存業務列・ID/sequence・人物UUID・履歴の不変と再実行0件を記録する。
3. 全workerを世代検証版へそろえ、旧フォームは409、新しいフォームは従来の条件下で登録/編集/削除できることを5マスタ・他社・同時操作で確認する。本番接続/本番移行/配備はこの作業では実施しない。
4. 切戻しで列をDROPしたり、IDを再採番したり、既存世代を再発行しない。追加列は旧コードの既存列SELECTを妨げないが、**保護前版へのマスタ書込再開は不可**。互換の保護版へ戻すか、マスタPOSTを運用側で遮断したままにする。実際の旧画面/worker構成の受入はQ11とリリース責任者が行う。
5. 復元では世代列もバックアップどおり保持する。復旧時には、承認された既存SECRET_KEYの更新等で旧フォームを失効させ、再ログイン/再読込後のフォームを使う。鍵更新やセッション/人物UUIDの変更を本PRが自動実行することはない。試験では鍵変更後の旧フォーム拒否を、再認証したクライアントでも確認する。

Q03 #283・Q08 #285/#297は基点mainに反映済み。人物UUID、Q11復旧コード、#304診断は再実装・変更しない。生成されたDB定義資料と契約fixtureだけは、5列とcontext processorの追加に合わせて更新する。

## 検証と5マスタの受入

| マスタ | SQLite | PostgreSQL |
| --- | --- | --- |
| 営業所 | 実ID再利用の旧編集/削除を409拒否、新割当を保持 | 別世代へのID再割当を注入して旧フォームを拒否 |
| 車種 | 同上、車両車種・取込対応を保持 | 同上 |
| 納入先 | 同上、新レコードとパトロール履歴を保持 | 同上 |
| 免許種別 | 同上、運転者免許JSONを保持 | 同上 |
| 内容区分 | 同上、新レコードとパトロール履歴を保持 | 同上 |

全5マスタの正当な編集/削除/再登録も実際のHTMLから得た署名で確認する。旧/改変/署名なし、会社・種別・ID・世代・操作の相違、他社の正当な署名、移行前の列欠落/NULLも検証する。拒否前後の全テーブル比較には、新割当、請求JSON/金額、点検結果、通知、監査、履歴、人物UUID、表示順を含める。

SQLiteでは「検証済みAを別接続で削除→同IDのBを登録→Bへ新割当→Aの保存を再開」の実競合を固定し、最終SQLの世代不一致で関連更新もrollbackされることを確認する。PGでは通常のsequence挙動と、復元/再採番障害を想定した強制ID再利用を区別する。既存PGの同時操作・他社・再試行の期待値/アサーションは維持する。

既存の直接POST型テストには、正常な新フォームを用意するtest-only adapterを追加する。署名が明示されたデータは置き換えず、新規の旧/署名なしテストはadapterを通さないPlain FlaskClientを使う。PGのフォーム準備は同期フックを有効にする前に行い、実POSTのSQL/ロック待機を隠さない。旧main対照実行は、世代機能がない版の旧APIをそのまま使う。業務の合格条件を緩めない。

移行は両DBで、既存値/人物/履歴/IDの保全、再実行、途中DDL失敗時の全rollback、不正既存世代の非修復、書込/読込ロック競合、custom trigger拒否を確認する。実行結果と最終headのCIはPRと作業証跡へ記録する。

## 残る実環境受入

正式な本番移行・停止/再開・鍵/旧フォーム失効・実容量/限定権限・旧版画面・復旧時間は未実施。DBA承認済みの隔離コピーで、実運用と同じ5マスタ件数とロック時間、既存trigger/RLS等の有無を確認し、Q11のバックアップ/切戻し手順と合わせてリリース判断する。既に旧フォームで消失したマスタや解除済み所属を、この修正が自動復活させることはない。過去の損傷はバックアップ・監査と業務判断による別作業である。以前の初期ITC所属の扱い等、#304で整理したデータ判定事項も勝手に修正しない。
