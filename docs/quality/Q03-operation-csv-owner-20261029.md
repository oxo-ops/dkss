# Q03 未確定運行実績CSVの所有者UUID

基準main 288261d。操作者修正PR #325とは独立したブランチ/PRで扱う。Q02 #313/#321はOCRのVehicleDocumentImportDraftが対象で、CSVのVehicleOperationImportDraftは別テーブルだった。import_owner.pyを変更せず、同じidentity_for_actor/owner_clauseの会社・認証UUID・現在ロール/ロック/会社有効状態の判定を再利用する。

## 再現と修正

修正前、AがアップロードしたCSVのプレビューは同username・同数値User.id・別UUIDのBにも200で表示された。SQLite/PostgreSQLで同じ期待404の試験を1件ずつ固定し、両方失敗した。

CSV受付にnullable owner_identityと(company_code,owner_identity)索引を追加し、新しい実HTTP受付時だけ認証UUIDを固定する。created_by_usernameは履歴として保持する。旧行はNULLのまま残し、username/数値ID/氏名から補完しない。ORMでの所有者付け替えも拒否する。

|経路|扱い|
|---|---|
|POST CSV受付・同内容の再送|現在の認証UUIDを保持。同じ所有者の未確定受付だけを再利用。Bの明示的な再アップロードは新しいB受付とし、A/旧NULLの受付を引き取らない|
|GET preview/result|会社＋UUID所有者を検証。旧NULLやBの別世代は404。結果画面も個人の受付として扱う|
|POST confirm（確認のみ/入力エラー保存/確定）|同じUUIDで再照合してから選択内容・処理状態・実績を保存。受付行→選択Vehicle（ID昇順）→Userの順で保持。Q02 #321のCompany共有ロックを再導入しない|
|API 受付からの車両追加|受付をロックし、既存マスタ検証後に所有者を保持。別人の受付から車両を追加しない|
|車両カルテ/登録待ちからのCSV原本取得|未完了の親受付は所有者を照合。完了済みの車両/登録待ち原本は既存の会社・車両/親子関係で共有する仕様を維持。Bが正当な現在権限で会社共有原本を読めることを、Aの個人受付継承と混同しない|
|登録待ちCSV反映|未完了親の原本利用前に所有者を確認。完了親の会社共有フローは維持。子テーブルへのUUID列の重複追加は行わない|
|取消|既存の「CSVの選択へ戻る」は画面遷移で、取消/削除POSTはない。受付を消す新APIや仕様は追加しない|

CSV受付応答はprivate,no-storeとする。既存OCR/日報No.10/No.11、Q08配送、マスタ世代、削除制限は変更しない。共通person_selection.pyも変更しない。

## 検証

test_q03_csv_owner.pyはSQLite/PGの所有者継承、確認/確定/API、旧NULL、同世代改姓・ロック解除・ログインID変更、他社同名、二重送信、エラー保存、認証後/解析後の失効、rollback/再試行、検証直後の別接続DELETE/Vehicle更新のロックを確認する。PGでは異なる受付の同時確定、同一受付の再送、同一マッピング新規作成の既存409後の正常再試行、登録待ち同時作成も確認する。

同一マッピングを同時作成した場合の既存一意制約409は維持する。別の対応キーの正常並行保存を両方成功させる試験と分け、競合を隠す期待値変更は行わない。

test_q03_csv_owner_storage.pyは両DBで旧原本/JSON/状態不変、旧NULL保留、再実行、既存Q02移行との順序独立、型/索引不整合拒否、DDL途中異常のrollback/再試行、明示URL必須を検証する。独立したQ03 CSV PostgreSQL Actionsを追加し、新規専用DB/所有スキーマだけで実行する。

既存Q05の正当なCSV作成fixtureには当該新規受付のUUIDを明示する。旧NULLを扱う独立試験はNULLのままで、製品の認可や既存assertは緩和しない。生成スキーマ文書/アプリ契約の変更はCSV列・索引・CSV専用キャッシュ応答フックだけ。
