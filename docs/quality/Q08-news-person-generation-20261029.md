# Q08 個人宛てお知らせの選択世代を保存時に照合する追加受入

main `288261d0549d7660466f4edc7bd7b30ec9e640a6`を基準とする追加修正。
固定288261dで実施済みの388件の移行検証には含めない。

## 原因と変更範囲

個人宛てお知らせの新規作成と宛先変更は、フォームを開いた時点の人物を
確認せず、POST時のcompany_codeとusernameで人物を解決していた。
A削除後、同username・同数値ID・別UUIDのBへの入替で、古いPOSTが成功し、
Bを所有者とする本文と添付が保存された。保存済み旧通知のUUID分離は対象外。

`itc_news_form.html`へ既存の署名付き選択証跡を追加し、`news.py`の両保存で
選択したtarget_valueを既存の`person_selection.validate`へ渡す。
証跡検証と人物のロックはファイル保存・News・Notification・監査の作成より前に実行する。
SQLiteはBEGIN IMMEDIATE、PostgreSQLは人物行のFOR SHAREを保存トランザクション中維持する。

共通関数には`selected_usernames=None`という省略可能なキーワードだけを追加した。
None時の既存フィールド検出、actor_only=True時の操作者のみ照合、署名形式、
409/400応答、会社境界、ロック、rollbackの契約を維持する。
Q03担当と事前に変更案と分担を確認し、Q03の操作者修正PR #325は共通ファイルを変更しない。
CSV所有者、通知配送の共通処理、日報の手動閲覧設定には変更を加えない。

## 修正前の保護期待

製品修正前に同一の回帰テストをSQLiteと隔離PostgreSQLで実行した。
各8件、計16件で、新規作成・宛先変更の古いPOSTがHTTP302となり、
期待した409に失敗した。証跡欠落・改変・別会社証跡も受理され、
計14個の失敗アサーションを記録した。正常対照は両DBで成功した。

## 修正後の追加受入

各12件、SQLite/PostgreSQL計24件が成功した。CSRFを有効化し、SQLiteのFKは
全接続で有効化した。PostgreSQLはlocalhostの専用クラスタ・ランダムなschemaのみ使用した。
添付は架空PDFで、外部配信だけを記録用mockに置き換えた。

| 受入条件 | 結果 |
| --- | --- |
| A選択後に削除、同username・同数値ID・別UUIDのB作成、新規POST | 409、部分保存なし |
| 同じ入替後に既存Newsを個人宛てへ変更 | 409、既存行・添付・監査を保持 |
| 証跡欠落・改変 | 両経路409、ファイル保存・配信なし |
| 他社証跡、他社のみ存在する宛先 | 409/403、他社データ変更なし |
| Bを新しいフォームで選び直す | BのUUIDで正常保存、Bだけが添付閲覧可 |
| 同UUIDの改姓 | 正常保存 |
| 選択後のロック・権限変更・人物消失 | 保存拒否 |
| UUIDがない旧User | usernameで補完せず409 |
| 新規の照合後、別接続から人物削除 | 実DBロックで削除側を拒否・rollback、A宛てを維持 |
| 宛先変更の照合後、別接続から人物削除 | 同上 |
| 保存済み旧Aの内容だけを編集 | 旧所有者UUID維持、Bへの付替えなし |
| 全員・管理者・会社・営業所宛て | 既存配信数を維持、編集時は再通知なし |

拒否時はNews・Notification・AuditLogの全列とローカル添付の全バイトを比較し、
変更が残らないことを確認した。実ロック試験は照合後の別接続DELETEが
SQLite busy/lockedまたはPostgreSQL 55P03となることを確認し、
保存後のA削除・B登録ではBの本文・添付閲覧が拒否されることも確認した。

既存Q02の正常個人宛て試験には実際のGETから証跡を取得する準備処理だけを追加し、
配信先・他社分離・編集・削除・監査・添付検証の期待値を変更していない。
Q08の既存CIへ追加24件を登録した。全CIの最終状態はPRのheadごとに確認する。

## 移行と導入

DB列・制約・索引・移行コマンドの変更はない。既存6処理の統合リハーサルへ
新しい移行を追加する必要はない。新版適用前に開いた個人宛てフォームは
証跡を持たないため拒否される。画面を再読込し、本人を確認して選び直す。
旧UUID不明の通知・履歴を新アカウントへ自動対応させない。

今回の修正前に誤送信済みのNews・通知の自動付替え・削除は行わない。
実データの調査と是正には、別途運用担当による対象特定・承認が必要となる。
No.10の未紐付け旧日報の閲覧P1は運転分析担当の仕様判断待ちとして維持する。

本番・Render・保護対象4DB・他担当worktreeは操作していない。
