# メール生成時の標準ヘッダー補完（非本番）

## 対象と理由
通常通知・MFA・メール変更確認の生成メールに Date と Message-ID がなかった。
RFC 5322 §3.6 は Date を必須、§3.6.4 は Message-ID を推奨している。
https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6

生成時の UTC 日付とランダム UUID による識別子を追加する。識別子の右辺は
既存 From の送信者ドメインのみ。端末ホスト名、プロセス番号、宛先、利用者 ID、
認証コードや本文を含めない。本文・TLS・認証・opt-in・タイムアウトは変更しない。

## 重複と配送の境界
1回の生成・SMTP 呼出しでヘッダーは1つずつ、新しい生成には新しい識別子を付ける。
識別子は配送完了証明でも、永続的な冪等キーでもない。自動再送は追加しない。
DATA 応答待ちの例外は配送の成否不明を維持し、QUIT エラー後の受理は #392 を保持する。
同一メッセージを将来キューで再試行する場合、生成済み ID を維持する別設計が必要。

## 未確認を残す
Brevo は事業者の識別までで、現在の契約・認証状態・警告原因・実到達は未確認。
この変更は SPF/DKIM/DMARC の認証や不審メール警告を解決した証拠ではない。
Message-ID の右辺は前後空白除去・IDNA変換・DNS名検証を行い、不正なら通信前に安全に失敗する。
SMTPUTF8/国際化アドレス全体の対応拡張は対象外。
実メール、DNS/設定変更、有料化、Render 問い合わせの再送はしていない。
品質 Word 第33.10〜33.13・35.4 の実受信証拠照合は別途必要。

## 検証
合成 SMTP による通常通知/MFA/メール変更の6通で単一ヘッダー・識別子相違・
ヘッダーパーサの欠陥なしを確認。既存30 SMTP境界と2 opt-in サブケースを保持。
既存の秘密非表示配送試験28件成功。外部送信も DB 初期化も行わない。
全回帰、GitHub CI、本番反映、実到達は未実施。
