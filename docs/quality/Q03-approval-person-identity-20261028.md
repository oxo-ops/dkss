# Q03 承認候補と点検対象者の本人識別

最新main bb3a118（Q08 PR #285の73fa933を含む）との隔離統合で検証。PR #283はドラフトを維持し、マージしない。本番DB・本番配信は操作していない。

## 統合で判明した原因と修正

初版Q03はUser.idを保存したが、SQLiteでは最大のUser.idを物理削除すると、同名再登録Bに同じ数値IDが自動採番される。候補Aの将来段階の詳細・Excel・添付権限をBへ継承し、ChecklistEventの数値IDもBと一致した。Q08は異なるアカウントUUIDで旧通知を正しく拒否するため、両者に矛盾が生じた。

また、候補の数値IDを保持しても、次段階へ進める通知の呼出元が現在のusernameから送信先を引き直すと、Q08へBのUUIDを渡してしまう。SQLiteとPostgreSQLで再現した。

Q03の数値IDと氏名は保持し、本人判定にはQ08のUser.account_identityを併記する。個人の対象者・実施者・承認者・パトロール作成者と対策担当者・イベント操作者を同じUUIDで記録する。approvals_jsonのcandidate_identities/approved_by_identity、運行判断のrequested_identities/judged_by_identityも併記する。数値IDだけの旧参照からUUIDを自動補完しない。

Q03の通知呼出元は、保存された候補・実施者・承認者・選定管理者・明示通知先のUUIDから現在の同一会社アカウントを確定し、Q08の既存APIへ渡す。証拠がない、矛盾する、削除された場合には別人へ送信しない。通知モデル・配信モジュールは変更しない。無関係な更新や同じ候補の再送で旧usernameを現在の別人へ再解決しない。保存トランザクション内でPostgreSQLのKEY SHAREを取得する。

## 維持する仕様

- 一般承認を許可した現在段階では、選択候補外の一般利用者も独立した権限で閲覧・承認できる。Bが自分のUUIDで承認することとAの候補権限継承を区別する。
- UUID不明の旧履歴は個人固有の閲覧・承認権限を保留し、正当な管理者と既存の一般承認権限による確認を維持する。
- 氏名・日時・username・旧数値ID・承認順序・差戻しイベントは保持する。既存のDriver削除制限は変更しない。
- 同一アカウントの改姓・ロック解除では同じUUIDを維持する。物理削除後の再登録は同じ人という申告だけでは旧UUIDへ接続しない。証拠と監査付きの本人確認・対応確定は別途必要で、今回その画面や一括対応ツールは作らない。
- 会社コードの境界とQ02の承認・運行判断の認可を維持する。添付・Excel・ダッシュボードも同じ本人判定を用い、承認印は保存済み氏名を使う。

## 移行・互換性・切戻し

mainからのQ03追加は4テーブルへ20列（nullable INTEGER 9列、VARCHAR(36) 9列、通知先対応用TEXT 2列）。初版#283の9列追加済み環境には11列を追加する。User/Notification等のQ08列はQ08の移行が担当する。User削除で歴史的証拠が消えるFKは追加しない。

推奨順序は、書込処理とジョブを停止、バックアップ取得、Q08のupgrade-account-identity、Q03専用スクリプト、列と件数・UUID安定性を確認後に新版起動。Q03はQ03_MIGRATION_DATABASE_URLを明示し、python tools/upgrade_safety_identities.pyを実行する。汎用DATABASE_URLやアプリ既定DBへのフォールバックはない。create_appやGETでQ03 DDLは実行しない。新規DBのcreate_allは新列を含む。

SQLite・PostgreSQLの使い捨てDBで、Q08→Q03とQ03→Q08の両順序、各再実行と逆順再実行をCLIで検証する。既存UserにQ08 UUIDを発行しても、過去通知owner_identity・監査actor_identity・Q03 UUID列・旧JSONはNULL/未特定のままとし、usernameから遡って帰属を作らない。初版Q03の数値IDのみのJSONも再移行でUUIDへ昇格しない。

Q03の移行は列追加のみ、JSONや履歴に更新・削除を行わない。PostgreSQLではadvisory transaction lockと同一トランザクションを使う。実DB量でのロック待ち・停止時間は未測定のため、運用適用前に検証が必要。列・UUID・履歴を削除するダウングレードはしない。アプリだけ旧コードへ戻すと旧username/数値IDの認可が復活するので、安全な通常運用の切戻しにはならない。該当機能とジョブの停止を伴う保守手順が必要。
