# Q02 並行確定のロック昇格を補修

PR #313で追加した本人確認の会社共有ロックと、既存の確定時会社排他ロックが競合した。通常CIとQ10は成功していたが、引渡し前の追加ロック確認で、実PostgreSQL上の同時確定を同期させるとSQLSTATE40P01 / DeadlockDetected、HTTP500/302を再現した。本担当の修正で導入した退行であり、隠さず補修する。固定基準mainは3582b969a79ce4f9a5b57e6d8171368a72607464。

HTTPの現在操作者確認はUserの共有ロックだけを取得する。確定前もUserのみを保護し、既存の会社排他ロックを取るときに共有→排他への昇格を発生させない。排他ロック取得後にCompanyをpopulate_existingで読み直し、失効なら登録しない。ワーカーの分類/公開は会社を書かないため、既存のUser/Company共有ロックと公開直前確認を維持する。UUID所有者の条件・失効条件は緩和しない。

実DBの新規回帰3件:
- 異なる2原本・同じ会社の並行確定が302/302で、2記録・2完了となる。
- 同一原本の並行送信が302/409で、登録は1回だけとなる。
- claim直後に別DB接続で会社を無効化し、リクエスト内に古いCompanyオブジェクトが残っていても404で止まり、記録0件・受付previewへ戻る。

修正前の2並行ケースはどちらもデッドロックで失敗。修正後は既存の所有者21件＋並行2件の23件、および会社失効ケースを加えた3件が成功。Q10の元の29件も入力/期待値を変えず再実行し全件成功（37.670秒）。最終CIは新しい専用24件、Q10 PG/ブラウザ、全体回帰を含めてPR本文と報告書で固定headとともに記録する。

DB定義・データ移行の追加はない。#307/#313の適用前提（バックアップ・書込/worker停止・明示移行、旧未登録受付の本人未確認保留）は維持する。既存環境/本番DBの読み取り/書き込み・本番S3/配信/デプロイ・main push・自動mergeは実施しない。実PostgreSQL試験は新規loopbackクラスタの架空データと専用schemaのみで、ワーカーの外部OCRは模擬する。
