# Q05 車両点検の業務日付・記録日時

2026年10月27日。品質改善計画の確認版は1.4。基準mainは `c811829b10963315c2dd062632a542257f3574b6`（PR #214の取込後）。

## 再現した不一致

車両点検のセル保存・詳細保存・完了の3経路では、新規レコード生成時に日本時間を設定する一方、直後の `checked_date` 更新で `datetime.now()` のサーバー時刻を上書きしていた。既存レコードの更新も同じ上書きを行っていた。新規登録画面・一覧の初期年月日もサーバー時刻に依存していた。

UTCサーバーの2026年12月31日15:30（日本時間2027年1月1日00:30）を模擬し、修正前は追加6テストのサブケースで26失敗を確認した。これは不具合26件という意味ではない。

## 修正の範囲

`dkss_app/checklists.py` の車両点検5経路（一覧、セル保存、詳細保存、完了、新規）で、既存の `get_user_local_now` を使い、リクエスト内の時刻を1回取得して共用する。

- 利用者のタイムゾーン設定を使用。空欄・不正値は既存の共通処理どおり日本時間へフォールバック。
- 年月日と選択日の初期値、新規・更新・完了の `checked_date`、差戻し後の修正・再申請イベント日時を同じ基準にする。
- 日・月・年の一覧で選択値が空文字の場合も、その表示単位の初期値へ戻す。年次一覧に日番号を使わない。
- 利用者が明示した対象年月日・過去日の点検対象は変更しない。実施対象日と操作日時を区別する。

過去データ、DB型、索引、認証・承認ルール、外部通知先、運転実績UI・乗務者の紐づけは変更しない。安全チェックリストの全履歴・全時刻を一括変更するものではない。

## 検証

`tests/test_q05_checklist_dates.py` に6テストを追加。Flaskの実ルートと一時SQLite、架空の点検・車両を使用し、外部AI・本番DBを呼び出さない。

| 観点 | 確認結果 |
| --- | --- |
| セル保存・詳細保存・完了 | 新規と差戻し済み既存レコードの両方で保存日時が利用者時刻になる |
| 設定未入力・不正タイムゾーン | 日本時間の年越し後として保存・表示する |
| Pacific/Honolulu設定 | 利用者側では前日の時刻で保存・表示する |
| 差戻し後の修正・再申請 | 点検記録とイベントの日時基準が一致する |
| 新規フォームと新規POST | 初期年月日と保存時刻が利用者設定を使う |
| 日次・月次・年次、選択値未指定・空欄 | 表示単位に合う初期選択を使う |
| 過去日を明示した入力 | 操作時刻が翌年でも入力した点検対象日を維持する |

修正後の関連回帰：追加6件、既存Q02の53件、主要業務52件、点検関連167件の計278件。実行結果の合格確認をもって記録する。実PostgreSQL・実ブラウザ・本番反映の完了とは区別する。
