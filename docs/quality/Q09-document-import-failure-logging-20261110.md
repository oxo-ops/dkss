# Q08/Q09 資料取込の失敗ログ

## 対象と境界

品質改善計画第26章のログ情報管理に対応する限定修正です。同期受付 `/vehicle/data-import` と進捗受付 `/vehicle/data-import/progress` の、捕捉済み読取・保存失敗5箇所を対象とします。これらは登録されたAPIですが、通常の非同期キューの利用率や本番での情報露出件数は調査していません。

既存の添付削除・SMTP/Web Pushログ修正を繰り返さず、未対応の原本名と例外全文の出力を除きます。例外本文にはSQL引数、原本情報、外部応答が含まれ得るため、traceback・例外クラス名も出力しません。利用者向けエラー案内、原本名、部分成功記録、認可、保存、rollback、再試行の有無、HTTPステータスは変更しません。

## 新しいログと調査手順

共通イベントは `DOCUMENT_IMPORT_FAILED mode=... stage=... error_type=... error_code=...` です。

- mode: 同期 `form`、進捗 `progress`。
- stage: 個別読取 `extract`、外側処理 `process`、同期保存 `persist`。`process` はDB保存を含むため、この値だけで失敗箇所を断定しません。
- error_type: `input`、`runtime`、`database`、`unexpected`。原因の確定診断や再送指示ではありません。
- error_code: 既存処理が取り出した完全一致の許可コードのみ。`OPENAI_NETWORK_OR_TIMEOUT`、`INVALID_INSPECTION_PDF` 等16種類です。その他は `unknown`。原文・SQL・ファイル名を追加して調査する運用には戻しません。

日時と採用コミット、経路・段階を照合し、必要なら合成資料で再現します。旧日本語ログ文言を対象とした監視がある場合は、採用時に新イベントとの対応を確認します。この修正自体では外部監視設定を変更しません。

## 検証

専用試験は最小Flask文脈から実際の両ハンドラーを呼び、抽出・DBをモック化します。合成原本名・例外本文・例外連鎖・クラス名・SQL引数がLogRecord/整形ログへ入らないことと、利用者への案内、部分成功、保存/rollback、中断、種別違い、検証専用受付を確認します。ヘルパーは未知値・文字列サブクラス・整形不能例外を拒否します。

既存の取込・所有者世代・キュー試験と全体回帰は別に記録します。専用試験の合格を実AI読取、本番DB/外部配信の受入やQ09全体完了としません。ログ保管・閲覧権限、handlerが後から追加する情報、他の例外経路は引き続き別の受入範囲です。本番反映は当該変更の承認後に行います。
