# Q08 通知所有者と再登録時の本人識別

調査・実装基点は main `6d7d8c9ccc7bd661cd86a6b5fa68b99da2a7c668`。本番DB・本番デプロイ・mainへのpush・自動マージは行っていない。
最終確認では main `c7efecbc3ede1c7c44855d1f768544531eee3172`（#277まで）へrebaseし、Q02・Q05・Q07の変更を保持した。
その後mainへQ04等がマージされたため、`7803605`（#286まで）を独立ブランチへ取り込んだ。製品コードは自動結合し、競合した生成スキーマ契約fixtureだけを結合後のORMから再生成した。

## 修正する問題

利用者Aの物理削除後、同じ会社・usernameで別人Bを登録すると、Aの通知がBの一覧に表示されていた。通知所有者・認証済みセッションをusernameと時刻だけで判定しており、時刻が一致した旧Cookieの再利用も確実には防げなかった。

`User.id` は物理削除後の履歴を残す識別子として不十分で、SQLiteでは数値IDの再利用も起こる。そこで、Userにアカウント世代を表すUUID `account_identity` を追加した。username・氏名・会社名の変更から独立している。同じ会社・usernameの新規Userでも新しいUUIDとなる。UUIDはORMの通常更新で変更できず、一意索引でも重複を防ぐ。人物の同一性を名前やログインIDから推定する仕組みではない。

DriverとUserは現在、会社・employee_id/usernameで関連しており、削除処理はUserも物理削除する。今回、`masters.py` の削除・再登録・同時操作ロジックは変更していない。Userの新規保存時にUUIDが発行されるため、既存の登録入口にも適用される。

## 通知と認証

- Notificationの `owner_identity` と会社で一覧、件数、最近の通知、詳細、遷移、パネル、既読、削除、復元、一括処理、時刻による取り消しを制限する。username一致へのフォールバックはない。
- 送信処理と各ワークフローの通知作成箇所は、選択済みの宛先UserのUUIDを記録する。送信中にAが削除されBが登録されても、宛先をBへ解決し直さない。新規ORM通知の共通フックも同一会社の一意なUserへ結び付け、未解決の場合は所有者を空のまま保持する。
- 認証CookieとMFA待機CookieにUUIDを保存し、毎回現在のUserと照合する。UUIDのない旧Cookie、別世代のCookieは失効する。パスワード更新時刻・会社・ロール・ロックの既存検証も維持する。
- Push購読にもUUIDを保存し、旧アカウントの端末へB宛て通知を送信しない。未移行の旧購読は送信対象外。新たな購読登録が必要となる。
- 通知添付と個人宛てNews添付も同じ本人識別で認可する。個人宛てNewsの作成時・宛先変更時にUUIDを記録し、旧usernameだけの添付を新利用者へ公開しない。

## 監査と履歴

新規AuditLogと整備記録イベントには、作成時の `actor_identity` と氏名のスナップショットを保存する。過去のusernameを現在のUserへ結び付けて表示しない。本人不明の旧監査記録・旧整備履歴は明示的に本人未確認として扱う。ログイン失敗の対象usernameを、本人の操作と断定して記録しない。

取込資料のアップロード履歴には従来usernameしかないため、現在のUser氏名へ引き直さず「記録時のID・本人未確認」と表示する。資料の値・原本・フィルター用の保存IDは変更しない。すべての業務イベントを新しい人物台帳へ一括移行する変更ではない。

スキーマ初期化時に監査ログを365日で自動削除していた呼び出しを外した。今回の移行と初期化は履歴を削除しない。既存の削除関数自体は残しており、保持期間の変更・明示的な削除は別の運用判断とする。

## 同一人物の復帰

既存User行を保持したロック・解除ではUUIDと通知・監査履歴を保持する。新しいUser行を作る操作は、同じusernameでも新しいアカウント世代となる。

物理削除済みUserのUUIDを新規Userへ移す復旧機能は提供しない。本人確認、根拠、承認、復旧対象、変更履歴が必要であり未解決事項とする。旧通知をusernameだけで新規Userへ紐付けることはしない。

## 段階的な移行手順

以下は運用担当者向け手順であり、本作業では本番で実行していない。

1. 既存のmain相当のスキーマ、バックアップ、停止可能な時間帯を確認する。Web・ワーカー・旧コードの書き込みを停止する。旧コードを並行稼働させたままアクセスを許可しない。
2. 新コードを使用する停止中の管理環境で `flask --app app upgrade-account-identity` を実行する。接続先を運用担当者が確認する。この専用コマンドは会社・通知・監査記録の削除や既存のブートストラップを行わない。
3. Userに欠けているUUIDだけを発行し、一意索引と通知・Pushの所有者索引を作成する。追加列はNULL許容で、再実行しても既存UUIDを変更しない。新規DBの `init-db` にも同じ追加処理を組み込んでいる。
4. **既存Notification・個人宛てNews・PushSubscription・AuditLog・整備記録イベントの所有者/操作者をusernameから補完しない。** 本人同一性を証明できない旧データは保持したまま非表示・送信対象外・本人未確認とする。正当な現利用者の旧通知も自動表示されなくなる点を事前周知する。
5. 隔離環境で旧通知が非表示、新通知の送信・既読・削除・復元、旧Cookieの失効を確認してから、新コードのみで再開する。全利用者の再ログインと必要な端末のPush再登録が必要。
6. 列の削除や旧コードへの単純な切り戻しは行わない。旧コードはusernameで旧通知を公開するため、障害時は停止を維持し、UUID認可を保つ修正版を適用する。

本移行は本番データの存在・重複・件数を調べた結果ではない。DDLは明示コマンド時のみで、import・通常GET・アプリファクトリーからは実行しない。SQLiteとPostgreSQLの旧スキーマで、内容保持・NULL隔離・UUIDの再実行安定性を検証する。

## Vehicle.deleted のNULLと台数上限

通常のORM新規登録では `deleted=False` を設定する。一方、既存列はNULL許容でサーバー側DEFAULTがないため、旧SQLやdeleted列を省略するINSERTではNULLが作れる。通常の現在のWeb登録経路でNULLが作られることや、本番にNULLが存在することは確認していない。

NULLを有効・無効のいずれにも変換しない。上限判定だけは「明示的に無効ではない行」を予約枠として数える。通常登録、Excel取込、新規車両のCSV紐付け、再有効化・一括有効化に適用する。他社の未確認行は数えない。NULLの有効・無効切替やNULL行を含む状態変更取込は409で停止し、状態確認を求める。表示上の有効車両件数をNULL込みへ再定義する変更ではない。

値の一括更新やNOT NULL制約追加は不要で、行っていない。NULL行の意味を確認して解消する運用は残る。既存の並行登録の台数競合を解決したという意味でもなく、その同時操作はQ04担当との調整対象とする。
