# 運転日報の本人未確定保留と再承認

登録済み日報は現在の氏名だけでは本人へ公開しない。Q08の会社・日報・アカウントUUID・原本識別指紋の永続証跡を認可に用いる。氏名が一致する別人の再登録によって、旧日報の一覧・詳細・集計・出力・AIへアクセスできたNo.10を防ぐ。

2026年10月29日の利用者決定に基づく変更であり、仕様書v0.25のS66にある「既存日報も一意な氏名で自動表示」を置き換える。U40の数値基準、Q08 No.11、Q02 OCR、Q03フォーム競合は変更しない。

## 候補と認可

`Resolver.candidate`は会社内の氏名・提供元・乗務員コード・運行日から候補を求める。候補自体は閲覧許可ではない。`Resolver.resolve`と`bindings`は有効なQ08永続証跡を必須とし、氏名・username・数値IDの再利用から証跡を補完しない。

新規取込では、同じ会社・提供元・乗務員コード・氏名について、対象運行日以前の現在UUIDに結び付いた有効な対応を根拠に自動確定する。日報の挿入とUUID証跡を同一トランザクションで保存する。コミット・ロールバック後は挿入時の能力を破棄する。既存日報の訂正・再読取は自動確定しない。

氏名だけの初回候補は本人未確定として保存する。管理者は既存の読取確認内で本人を選択でき、根拠がなければ保留できる。全件の再確認を通常操作へ追加するものではないが、信頼できる対応がない初回については確認が必要となる。既に有効なUUID証跡を持つ権限は維持する。

## 表示と出力への影響

本人未確定の日報は一般利用者の一覧・詳細・件数・距離・比較CSV・PDF・AI入力・保存済みAI結果の現在の根拠から除外する。本人画面と個人向けPDFは、表示対象なしが実績0件を意味しないことを説明する。別人の保留件数や氏名を一般利用者へ知らせない。

会社内の管理者の原本閲覧・会社／営業所の原本集計は維持する。原本の数値・氏名・username・過去のUUID証跡は書き換えない。本人未確定の日報詳細では、既存の本人閲覧設定を開いて確認できる。

## 移行設計

新しいテーブル・列・一括更新は不要。Q08 #297の証跡テーブルを再利用する。適用後は読取時の認可で保留となり、氏名・username・社員番号・取込日を使うUUIDの自動補完は実施しない。

1. 配備前に、同じ会社の日報・閲覧設定・最新のUUID証跡を読み取りで照合する。証跡欠損、現行UUID不一致、原本指紋不一致、ロック／対象外利用者を再確認対象へ分ける。現在氏名が一意なだけでは確認済みにしない。
2. 原本ID単位の対象一覧と、本人画面・比較期間の件数／距離の変化を業務責任者が確認する。本番対象件数は本作業で取得しない。
3. `init-driving-access`が必要な環境では従来のQ08手順で実施する。この初期化はテーブル準備だけであり、旧日報の本人を確定しない。再実行しても未確定行を現在Userへ補完しない。
4. 管理者が原本と信頼できる本人資料を確認し、必要な日報だけ明示設定する。不明な原本は保留を維持する。
5. 適用後、管理者の原本合計を維持し、本人の確認済み日報だけが一覧・出力・AIへ入ることを照合する。移行確認の再実行で権限・原本が変化しないことを確かめる。

認可コードを旧版へ戻すと氏名だけの公開が復活し得るため、障害時は旧版への単純な戻しではなく本人向け機能の一時停止を含めて責任者が判断する。原本のバックアップを削除・書き換えして保留を表現しない。

## 管理者の再承認手順

1. 自社の運転実績で日報を開き、原本を照合する。
2. 「乗務員の変更・本人表示の解除」を開き、原本の本人に対応する現在のアカウントを確認する。同姓同名は所属・社員IDだけで推測せず、確認資料を用いる。
3. 本人アカウントを選び「閲覧設定を保存」を押す。既存の会社・管理者権限・原本版の検証を維持し、Q08の対象UUIDと操作者証跡を追記する。
4. 本人の一覧・数値・出力・AIの対象を再確認する。別の旧日報まで公開されたと扱わない。公開しない場合は「未設定・公開しない」を保存する。

Q03側の選択から保存までのアカウント再作成競合は別担当の範囲であり、この変更で解消済みとは扱わない。

## 受入条件

- SQLiteはFK有効、PostgreSQLは独立したlocalhostの使い捨てDB／schemaで確認する。
- A削除後の同姓同名・同username・同数値IDの別UUIDのBに、旧原本とCSV/PDF/AIを公開しない。別会社も拒否する。
- 新規の氏名だけの候補、確定コード付きの新規取込、既存日報の再実行、トランザクションの失敗を区別する。
- 管理者の原本合計と既存UUID権限を維持し、指定日報の再承認だけを反映する。
- 初期化再実行と閲覧GETでUUIDを補完しない。保存済みAIも現在の認可で再評価する。
- `tests/test_driving_verified_readership.py`は危険な旧200応答を期待する現象記録ではなく、修正後の拒否を求める受入試験とする。

事前の現象記録14件は調査ブランチの`85a70c1`に保持する。そこでの200応答の成功は修正後の安全性合格ではなく、今回の拒否試験へ置き換える。Q08確定済み権限・Q03本人識別等の既存23件は別に回帰する。
