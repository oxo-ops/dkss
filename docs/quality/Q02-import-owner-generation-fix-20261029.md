# Q02 OCR受付の本人世代・アクセス制御修正

基準main `0832720`（#283・#297マージ済み）。Q10 #294は修正前PG29件中12失敗を再現。OCR抽出中に旧Aを削除し同社・同usernameの別UUIDのBを作ると、旧受付previewと原本がBへ200/200、原本bytesも一致した。Q08/取込以外の人物ID設計は再実装しない。

## 保存する証拠と不変条件

VehicleDocumentImportDraftへnullableのowner_identity VARCHAR(36)を1列追加し、Q08のUser.account_identityを受付時点で固定する。Userへの削除連動FKを付けず、A削除後もAのUUIDを保持する。created_by_usernameは受付時の表示/証跡として保持し、認可には使わない。同じUUIDの改名・ロック解除は本人のままとし、同じ数値User.idでも別UUIDなら別人とする。

新規のキュー受付と同期/stream受付は外部OCRより前にUUIDを保持する。ORMの新規行ライターも既存Q08のUUIDを使い、既存行は自動補完しない。混在資料の振分け子には親のUUIDを明示的に渡す。upload_keyによる冪等性、件数制限、行IDの生成も本人UUIDへ統一する。

## 所有者判定の棚卸し

| 経路 | 修正・保持する境界 |
| --- | --- |
| queue.enqueue / 同期・stream受付 | 会社・現在UUID・現在権限を確認して保存。別世代の同じupload_keyは旧受付を返さない |
| claim後・分類後・再振分け・抽出後 | owner_availableはUUIDと会社、現在admin/itc・非ロック・会社有効状態をDBの列で再確認。キャッシュ済みUserで判定しない |
| 結果公開 | preview生成後にも再確認し、短いcommit区間でUser/Company共有ロック。失効ならread_error、previewを空にして原本は保持。実行開始済みの外部APIを強制中止できるとは主張しない |
| 状況・受付一覧・確認画面・請求候補・確認保存 | 会社＋UUIDで照合。編集保存/確定前に現在権限を再確認。古い名前からBを探し直さない |
| 未登録原本・取消し・再試行・種別変更 | 同じUUIDの所有者のみ。private/no-storeを付け、種別確認の署名にも操作者UUIDを含める |
| 登録済み資料の種類訂正 | 既存の会社内管理者権限を維持。新しい訂正受付は訂正者のUUIDで作り、元受付の所有者を書き換えない |
| 保留車両の資料原本 | 確定済みのPendingRecordに結び付いたcompleted資料という会社共有を維持。未登録previewが紛れた参照は拒否 |
| 同じDocumentDraftを使うExcel確認・取消し・登録 | 共通モデルの所有者境界をUUIDへ揃える。CSVのOperationDraftや既存の会社共有業務データの意味は変更しない |
| 登録済み整備・点検・日報の原本 | 既存の会社/車両/記録参照チェックを維持し、所有者限定へ変更しない |

Q08のUser UUID生成・セッション・通知、Q03の承認者/候補/履歴、Q04/Q05等は変更しない。

## 既存DB・旧受付

適用は書込/ワーカー停止とバックアップ後、Q08のUser UUID移行済みであることを確認し、`Q02_IMPORT_OWNER_MIGRATION_DATABASE_URL=... python tools/upgrade_import_owners.py` を明示実行してから新版を起動する。DATABASE_URLへフォールバックしない。列と非一意インデックスのみ追加し、起動・GETでDDLを行わない。

既存行のowner_identityはNULLのままにし、原本・preview/result JSON・username・登録結果を書き換えない。現在の同名Userからの自動補完は安全な本人証明にならない。旧未登録受付は保留され、旧usernameからの再試行/閲覧を許可しない。正しい利用者が手元の原本を新しく受け付けるか、別途の根拠付き本人確認を要する。旧データを削除せず、証拠のない所有者付替え機能は追加しない。登録済み資料の会社内共有は継続する。

SQLite/PGで追加と冪等性、旧原本/JSONが不変・NULLのまま、非互換の既存owner型で停止することを検証する。旧コードへ切り戻すとusername判定の漏えいが復活するため、列を削除せず保守停止を継続する。実DBへは実施していない。

## 検証・Q10への受入条件

新規19件（SQLite10/PG9）でHTTP9経路の拒否と不変、別世代upload_key、同UUID改名後の閲覧/冪等性、ロック解除再試行、混在子の継承、preview生成直後の世代交代、旧行非補完、所有者不変、移行を確認。既存のキュー・失効・種類訂正・会社共有・請求/保留に関する68件も成功。外部OCRのみ模擬、DB/HTTP/取込は実経路である。

Q10のOCR8ケースは変更せず成功した。日時500は別PR #307で修正するため、このPR単独のPG全体を全件成功とは扱わない。両修正の隔離統合で、元の失敗12件を含む29件、Q02/Q08、PC/mobile emulation、全体回帰を実行し、固定head・CIをPR本文で引き渡す。受入テストの入力・期待値を緩和しない。本番DB/S3/配信/デプロイ・main push・自動mergeは実施しない。
