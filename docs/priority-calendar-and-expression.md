# AND条件と暦月間隔の事実表示

## 今回の範囲

`vehicle_priority_timing_sources` に検証済みの条件グループを追加し、`timing_condition_payload` でJSONにできる形式を提供する。純粋な非本番接続部である。後続の隔離HTTP/API・画面接続は `priority-condition-preview-api.md` に記載する。通常環境には接続しない。この直列化関数は信頼できる内部の検証結果専用であり、リクエストから作ったdataclassの型だけで検証済みと認める境界ではない。既存の採点、並び順、DB、保存提案、回答、運行判断を変えない。

取得した原文条件をAND・OR・単独のまま保持する。表示する前に、既存の出典版・適用条件・明示した対象事象の検証に加え、AND各条件の起算、単位、値、暦計算、距離計算、到達状態も照合する。元の計算結果を無検証で「検証済み」と表示しない。

## 根拠が明確な表示

- 暦日条件だけのAND：各条件の成立日をすべて計算できる場合、全条件が成立する日は最も遅い日となる。個々の条件と日付を省略しない。この日付を法定期限へ読み替えない。
- 暦日条件だけのOR：いずれかが成立する日は最も早い日となる。既存ORの採点用入力は保持する。
- 距離を含む条件：読取日における条件ごとの到達状態、距離の残量、暦日条件の成立日は表示できる。走行距離が条件値に到達した実際の日は記録間から推定せず、グループ全体の成立日はnullとする。すべて到達済みでも、観測日を実際の到達日へ転用しない。
- 計算できない要素、不一致、欠損がある場合：今回の表示は未検証の行を公開せず、条件グループをnullとして具体的な不足を返す。これはデータの状態であり、第4の優先度ではない。検証済み部分だけの個別表示は今後の拡張とする。

## 月間隔

既存コードと同じく、正確な起算日から指定月数を直接加え、対象月に同じ日がなければその月の最終日に合わせる。月数回繰り返して1か月ずつ加える方式にはしない。

例：1月31日＋2か月は3月31日。1月31日＋1か月は通常年なら2月28日、うるう年なら2月29日。2月29日＋12か月は翌年2月28日となる。

算出日、残日数、経過日数、起算日から算出日までの実際の日数は事実として表示する。閾値の単位 `calendar_months` と残量の単位 `days` を分ける。実際の日数を表示しても、その比率を月間隔の90％判定へ流用しない。

## 未定義のため加点しない範囲

仕様書の対応時期Tの表は「期限まで30日以内又は指定間隔90％以上」としているが、次の算定方法は指定されていない。

1. AND全体の接近を、全部の条件の接近、1条件の接近、又は別方式のどれで定義するか。
2. 月間隔90％の分母・端数を、暦月の完了数、実際の期間日数、暦月内の端数などのどれで定義するか。
3. 距離と暦日が混在するANDの成立日をどう表現するか。現在のデータから実際の距離到達日を作ることはできない。

今回のAND出力は、全条件が到達していても採点用TimingFactを発行しない。ANDの事実表示は浮動小数点による90％採点比較を必要とせず、許容範囲内の正確なDecimal計算を保持する。個々の条件を別々に最大採点へ渡すとANDがORへ変わるためである。暦日だけのAND成立日も、今回の変更では並び順や期限点へ使用しない。月間隔は従来どおり検証済み期限日だけを既存の単独／OR入力として利用する。暦月90％は不足事項として残す。

## API／画面へ進められる接続

採点方法の決定を待たず、次の読取り専用表示を別作業として進められる。

1. 既存の隔離プレビューの管理者・会社・車両のガードを再利用し、サーバ側で登録された対応と最新の取得値を照合する。ブラウザから確認済みフラグや別車両の対応を受け取らない。
2. 優先度結果とは別フィールドに、版付き `timing-condition-view-v1` を付ける。会社・車両・対象・事象・基準日・rule_key・snapshot_hashを同時に返す。同じ基準IDでも車両をまたいで再利用しない。
3. 高・中・低と点数を変更せず、説明欄に「すべての条件（AND）」等、原文、各閾値、単位、起算日、記録基準日、算出日、残量を表示する。ANDは「条件の事実表示、期限点には未反映」を併記する。
4. 月数と日数を別に表示し、比率メーターは作らない。APIの `scoring_input_emitted` は採点用入力を発行したかであり、最終的に点数へ採用されたことを意味しない。
5. 原文はtextContent又はテンプレートのエスケープで文字として表示する。JSON内の原文をHTMLとして挿入しない。旧表示の取消・切替・戻る時も、取得値が合わなければ古い条件を残さない。

後続の合成プレビューAPIと画面コードへの接続は `priority-condition-preview-api.md` の範囲で実装した。実ブラウザ受入と通常環境接続は未完である。採点の不足と表示作業の着手可否を分け、専門家確認を開発・合成試験の待ち条件にしない。本格運用前の実例確認は継続する。

## 根拠と境界試験

確認元は実際の2026年11月10日更新仕様書の「車両カルテの対応優先度」「対応時期T」「入力と根拠の成立条件」「K68」、および既存 `dkss_app/maintenance_timing.py` のAND集約と暦月計算である。新しいメーカー周期・法定期限・安全性の自動判定は追加していない。

月末、うるう年、直接加月、AND最後の成立日前日・当日・翌日、距離との混在、距離の読取日と基準日の差、要素欠損、不正起算日、改変された結果、JSONでの単位・原文・スコープ保持を合成値で検証する。
