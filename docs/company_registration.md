# 会社の登録URL・利用者承認仕様

## 目的と状態

会社ごとにボタン1つで登録URLを発行し、複数人へ同時配布する。URLは登録申請の入口であり、ログイン権限・管理者権限・業務データ閲覧権限ではない。新方式は #385 で本番反映済み。HTTPS上の登録URL発行でCSRF確認エラーが判明したため、本修正でReferer方針を調整する。修正版の本番反映結果はリリース記録で管理する。

## 正常フロー

1. ITCが契約・導入で会社と顧客責任者を確認する。ITC管理の会社行から「登録URL・申請」を開き「登録URLを発行（7日間）」を押す。
2. 発行画面のURLをコピーし、責任者と利用者へ一度に配布する。URLはハッシュのみDB保存し、生URLは発行応答で1度だけ表示する。再表示には再発行が必要。
3. 各人が会社名を確認し、ログインID・氏名・本人が決めたパスワード等を入力する。登録申請はUser/Driverと別のテーブルに置き、承認までログイン不可。
4. 初回管理者のみ、ITCが導入時に確認した顧客責任者本人と申請の対応を契約時連絡先への電話等の独立した経路で確認し、確認方法・日付等を記録して承認する。先着・氏名一致・URL所持だけでは認めない。ITCが本人のパスワードを入力・閲覧する操作はない。
5. 初回管理者が通常ログインする。以後は会社側管理者が申請者の所属・本人を確認し、一般利用者または会社管理者として承認する。管理者は複数人にできる。ITCによる通常利用者の個別承認は不可。
6. 承認でUser/Driver/監査/会社利用集計を同一トランザクションに反映。申請のPWハッシュは消去する。メール・プッシュ・AI呼出しは行わず、承認完了は会社内で伝える。

## 期限・再発行・中断

- 画面発行期限7日間。サービス内部は1〜30日に制限。1人の申請や承認で共通URLは消費しない。
- 申請の承認もURLの期限内に必要。期限切れは新URLから再申請する。
- 再発行は旧URLすべてとその未承認申請を失効する。明示失効も同じ。承認済みUserには影響しない。発行ボタンの重複押下は最新URLのみが有効。
- 無効な入力は同じURLのフォームへ戻し、パスワードは再表示しない。CSRF切れは元の登録入口を開き直せる。承認/却下の繰返しは二重作成しない。
- 会社ごとの未承認申請上限1000。管理画面は未処理を古い順に優先、50件ずつページ送り。
- 期限切れ申請のハッシュは新しい申請時と明示清掃CLIで消去する。承認・却下・失効もハッシュを消去。清掃CLIの定期運用は別途設置が必要で、このPRでは自動実行されない。

## メール・MFA

個人メールなしは既存設定MFA OFFで利用可能。MFA ONなら既存メール認証に必要な有効メールアドレスを申請・承認時に要求する。メールを登録しただけで所有者確認完了とはしない。SMTP配送、MFAの成功まで本機能が保証するものではなく、認証設定や秘密鍵の変更・MFA弱化は行わない。将来メールなしでMFA必須にする場合は別の認証手段を設計する。

## セキュリティ境界

- 256bitランダムURL token、DBはSHA-256ハッシュのみ。会社/用途固定、期限/失効はサーバー判定。
- 全POSTはCSRFとレート制限を適用。会社停止中不可。公開登録から会社・roleの任意指定を拒否。
- 会社行ロックで発行/申請/承認/失効を直列化し、User作成後の確認ではなく同一トランザクション内で初回判定する。既存Userの会社+ID一意制約も維持する。
- 承認済Userのみ既存のsession/account_identity/パスワード期限/会社停止/MFA保護に従う。
- 画面はno-store / Referrer-Policy: same-origin / noindex。同一オリジンのフォームPOSTではRefererを送り、HTTPSのCSRF厳格検証を維持する。外部オリジンにはRefererを送らず、招待URLの外部漏えいを抑える。URLはブラウザ履歴・配布チャネル・上位proxyアクセスログに残り得るため、共有範囲を社内に限定し、漏えい時は失効する。基盤ログのクエリ削除は導入時確認事項。
- OWASPの最小権限・全要求での認可・会社境界の考え方を参照。認証済みITC担当の実際の本人確認をテキスト入力だけで技術的に証明することはできない。

## 導入と旧方式からの移行

**互換性変更あり**：従来の `/register?company_code=...` は期限も承認もないため、本方式と併存すると申請承認を迂回する。このPRは旧URLからの新規登録を停止し、有効な新URLを要求する。既存User・Driver・パスワード・ログインURLは変更しない。

本番配備前に利用者へ新URLへの切替を案内し、管理者に操作を説明する。旧URLをそのまま有効に保つ案は非推奨。期限限定の互換受付を望む場合も旧入口をpending化する別設計が必要。切替・配備・DB変更は別途承認を得て行う。

明示移行: `flask --app app upgrade-company-invites` は新規2表のみ追加し既存データを消去しない。Web読取・import時に移行を自動実行しない。新規DB bootstrapでは通常create_all対象になる。

清掃: `flask --app app expire-company-registration-applications` は期限切れ未承認申請をexpiredにしPWハッシュを消去する。既存Userは変更しない。

HTTPS CSRF修正はレスポンスヘッダーと回帰試験のみで、追加DB移行・MFA設定変更・通知送信を伴わない。
