# 会社の登録URL・利用者承認仕様

## 目的と状態

会社ごとに「管理者用」と「一般利用者用」の2種類の登録URLを、それぞれボタン1つで発行する。両方とも期限内に複数人へ同時配布できる。URLは登録申請の入口であり、ログイン権限・管理者権限・業務データ閲覧権限ではない。

**状態の訂正**：#385で反映したのは1種類の共通URL方式であり、ユーザーが意図した2種類方式ではなかった。本修正は2種類方式のコード・仕様・試験を追加する段階で、本番反映済みとは扱わない。既存の共通URLと未承認申請は期限・明示失効まで従来の承認方式を維持し、自動変換しない。

## 正常フロー

1. ITCが契約・導入で会社と顧客責任者を確認する。ITC管理の会社行から「登録URL・申請」を開き「管理者用登録URLを発行（7日間）」または「一般利用者用登録URLを発行（7日間）」を押す。
2. 発行画面のURLをコピーし、管理者用は管理者候補へ、一般利用者用は一般利用者へ、それぞれ複数人に一度に配布する。URLはハッシュのみDB保存し、生URLは発行応答で1度だけ表示する。再表示には再発行が必要。
3. 各人が会社名を確認し、ログインID・氏名・本人が決めたパスワード等を入力する。登録申請はUser/Driverと別のテーブルに置き、承認までログイン不可。
4. 初回管理者のみ、ITCが導入時に確認した顧客責任者本人と申請の対応を契約時連絡先への電話等の独立した経路で確認し、確認方法・日付等を記録して承認する。先着・氏名一致・URL所持だけでは認めない。ITCが本人のパスワードを入力・閲覧する操作はない。
5. 初回管理者が通常ログインする。以後は会社側管理者が申請者の所属・本人を確認し、申請元URLの種類に一致する権限で承認する（管理者用→会社管理者、一般利用者用→一般利用者）。一般用から管理者への昇格は不可。管理者は複数人にできる。ITCによる通常利用者の個別承認は不可。
6. 承認でUser/Driver/監査/会社利用集計を同一トランザクションに反映。申請のPWハッシュは消去する。メール・プッシュ・AI呼出しは行わず、承認完了は会社内で伝える。

## 期限・再発行・中断

- 画面発行期限7日間。サービス内部は1〜30日に制限。1人の申請や承認でどちらのURLも消費しない。
- 申請の承認もURLの期限内に必要。期限切れは新URLから再申請する。
- 再発行は同じ種類の旧URLすべてとその未承認申請を失効する。他方の種類と旧共通URLは失効しない。明示失効も同じ。承認済みUserには影響しない。発行ボタンの重複押下は同じ種類の最新URLのみが有効。
- 無効な入力は同じURLのフォームへ戻し、パスワードは再表示しない。CSRF切れは元の登録入口を開き直せる。承認/却下の繰返しは二重作成しない。
- 会社ごとの未承認申請上限1000。管理画面は未処理を古い順に優先、50件ずつページ送り。
- 期限切れ申請のハッシュは新しい申請時と明示清掃CLIで消去する。承認・却下・失効もハッシュを消去。清掃CLIの定期運用は別途設置が必要で、このPRでは自動実行されない。

## メール・MFA

個人メールなしは既存設定MFA OFFで利用可能。MFA ONなら既存メール認証に必要な有効メールアドレスを申請・承認時に要求する。メールを登録しただけで所有者確認完了とはしない。SMTP配送、MFAの成功まで本機能が保証するものではなく、認証設定や秘密鍵の変更・MFA弱化は行わない。将来メールなしでMFA必須にする場合は別の認証手段を設計する。

## セキュリティ境界

- 256bitランダムURL token、DBはSHA-256ハッシュのみ。会社/用途固定、期限/失効はサーバー判定。
- 全POSTはCSRFとレート制限を適用。会社停止中不可。公開登録から会社・roleの任意指定を拒否。
- 会社行ロックで発行/申請/承認/失効を直列化し、User作成後の確認ではなく同一トランザクション内で初回判定する。既存Userの会社+ID一意制約も維持する。
- 承認済Userのみ既存のsession/account_identity/パスワード期限/会社停止/MFA保護に従う。
- 画面はno-store / Referrer-Policy: same-origin / noindex。同一オリジンのフォームPOSTではRefererを送り、HTTPSのCSRF厳格検証を維持する。外部オリジンにはRefererを送らず、招待URLの外部漏えいを抑える。URLはブラウザ履歴・配布チャネル・上位proxyアクセスログに残り得るため、共有範囲を社内に限定し、漏えい時は失効する。基盤ログのクエリ削除は導入時確認事項。
- OWASPの最小権限・全要求での認可・会社境界の考え方を参照。認証済みITC担当の実際の本人確認をテキスト入力だけで技術的に証明することはできない。

## 導入と旧方式からの移行

**互換性変更あり**：従来の `/register?company_code=...` は期限も承認もないため、本方式と併存すると申請承認を迂回する。このPRは旧URLからの新規登録を停止し、有効な新URLを要求する。既存User・Driver・パスワード・ログインURLは変更しない。

本番配備前に利用者へ新URLへの切替を案内し、管理者に操作を説明する。旧URLをそのまま有効に保つ案は非推奨。期限限定の互換受付を望む場合も旧入口をpending化する別設計が必要。切替・配備・DB変更は別途承認を得て行う。

明示移行: `flask --app app upgrade-company-invites` は招待・申請の2表と、今回のpurpose列を不足時のみ追加し既存データを消去しない。Web読取・import時に移行を自動実行しない。新規DB bootstrapでは通常create_all対象になる。

清掃: `flask --app app expire-company-registration-applications` は期限切れ未承認申請をexpiredにしPWハッシュを消去する。既存Userは変更しない。

以前のHTTPS CSRF修正単体はレスポンスヘッダーと回帰試験のみで、追加DB移行・MFA設定変更・通知送信を伴わなかった。今回の2種類方式には下記purpose列の移行が必要。

## 2種類方式への移行と受入

- 明示的な既存の招待schema移行で `company_registration_invite.purpose` を追加する。既存行は `legacy`、新規画面発行は `admin` または `user`。読み取りやフォーム表示で移行しない。配備前に承認済みの移行手順で適用し、追加列は残す。2種類のURL発行後はpurposeを理解しない旧コードへ直接ロールバックしない（旧コードは一般用申請を管理者として承認できてしまう）。ロールバック先はpurpose-aware版に限定する。やむを得ず旧版へ戻す場合は受付・承認を停止し、承認済みアカウントを保持したまま2種類の有効URLと未承認申請を明示的に失効させる、別途承認された運用手順を必要とする。
- 管理者不在時、一般利用者申請は待機できるが承認できない。最初の管理者は管理者用URLから申請し、ITCによる本人・責任者確認と確認記録を必要とする。管理者成立後は会社管理者が同じ管理者用URLから複数の管理者を承認できる。
- 種別改ざん・会社越境・一般用申請の管理者承認を拒否する。2種類同時有効、各複数申請、同種のみ再発行失効、明示失効、期限切れ、旧共通URL互換、繰返し承認の回帰を確認する。
- 既存のパスワード忘れの回復機能ではない。招待の新規発行・登録申請・本番schema移行は、この文書更新だけでは実施されない。

### Live 基点限定リリースの先行移行 runner

`tools/predeploy_company_invites.py --expected-sha <審査済みの完全40桁SHA>` は
Render Pre-Deploy 用の限定 runner である。期待SHAはデプロイ設定に固定し、
実行環境自身の値を期待値として流用しない。対象は現行の新DBのみで、旧再構築DBは対象外。
TLS verify-full と CA 検証を維持する。既存招待・申請テーブルが無い環境、
想定外の purpose 列定義、別DB、別SHAでは停止する。

候補に登録された `upgrade-company-invites` CLI のみを実行する。
init-db、reset、管理者作成、URL発行は行わない。
接続10秒・ロック待ち5秒・SQL60秒・子プロセス全体120秒を上限とする。
標準出力と標準エラーはOSレベルで破棄し、外には固定の成功/停止識別だけを返す。
移行前後に招待・申請の件数、および legacy/typed の件数保持を確認する。
件数検査は同数更新を証明するものではなく、作業中の書込停止が別途必須である。

Pre-Deploy の失敗は新コード起動を阻止する。ただし移行後検査失敗やタイムアウトは
DBコミット前後を断定できない。自動再試行・再DROPをせず、列と現在状態を安全に確認する。
公開受付を止めた状態でのみ実行し、全旧workerの終了と候補SHA稼働を確認してから
公開を戻す。Render Maintenance Mode は全公開画面を503にするが、private networkや
SSHの書込までは遮断しない。進行中要求・別経路の書込が無いことも確認する。

既存Start CommandのSHA固定条件も候補SHAへ更新する必要がある。
DB/TLS/CAの条件は変更しない。typed URL発行前に中止する場合は、旧Start設定と
空のPre-Deploy設定を戻し、旧Liveの稼働を確認してからMaintenanceを解除する。
typed URL発行後の旧版ロールバック禁止条件は前節に従う。
