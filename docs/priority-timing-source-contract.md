# Adopted timing shadow source contract

`vehicle_priority_timing_sources.bridge_adopted_timing` is a pure, opt-in adapter. It does not read databases, fetch references, inspect narrative severity, determine operating permission, modify saved proposals, or enable production. Expert/real-case validation is required before operational adoption, not before local development.

The host supplies the original adopted rule and its exact `timing_facts` object from `AdoptedMaintenanceTimingService`. A frozen `TimingBinding` identifies company, vehicle, target, event, reference date, rule key, document checksum and the exact pair's `timing_snapshot_hash`. It also identifies separately reviewed event evidence and references. Each selected reference additionally has a frozen `ReferenceBinding(reference_id, document_checksum, reference_hash)`. The checksum must equal the adopted document checksum, and `reference_hash` must match `reference_snapshot_hash(reference)`, covering every Reference field including its exact version. Changing the reference version or the checksum mapping invalidates that binding. The host must establish the version-to-checksum correspondence from the actual source; a matching supplied hash is not an independent source review. The binding is trusted host testimony, not user/AI JSON. Hash equality detects changes; it does not establish truth or authenticate the host.

Required rule fields are `action`, `cycle`, `relation`, `criteria`, `source_quote`, `vehicle_applicability.status=conditions_matched`, and `analysis_adoption` with adopted status, rule key, document ID/checksum, source URL and knowledge/vehicle source IDs. The upstream adoption service owns model, engine, usage conditions, original quotation and public document version checks. The caller must preserve those complete fields, not synthesize an adopted marker.

The caller explicitly verifies origin and same-event linkage. Current/open `Evidence` must already carry the exact target/event/company/vehicle scope; historical replacement or inspection records are never converted into current defect evidence by this bridge. All timing provenance IDs are returned separately, including the original historical baseline and knowledge/vehicle IDs. Consumers must retain the original snapshot and provenance alongside emitted facts for audit. Returned facts cite only the caller's reviewed event evidence and adopted manufacturer reference. Reference URL and quotation must match adoption and rule; issuer, title, version, verified and applicable are mandatory. `reference_checked_on` must equal the explicit assessment date. This records a host review assertion, not an online freshness check. The host must establish reference validity/applicability for that date and invalidate the binding when evidence, applicability or version changes.

Only `single` and fully calculable `any` are converted to scoring facts. Criteria and results must agree on metric, threshold, status, calendar arithmetic, meter subtraction and origin. Reached and remaining values are validated; month arithmetic retains end-of-month clamping. All combination rules are withheld intact in the host snapshot, with an explicit missing-condition explanation and no emitted facts. Incomplete OR rules are also withheld as a whole. No minimum-score substitute is invented.

Distance and day ratios use exact decimal checks before conversion to native finite numbers accepted by the existing scorer. Any lossy conversion or change across the 90%/100% scoring boundary is withheld. Calendar-month rules emit only a verified deadline date and explicitly report that the 90%-of-month-interval calculation is unsupported. They never invent elapsed months or divide elapsed days by a month count. No legal deadline is inferred from manufacturer intervals.

Malformed identities and unverified provenance raise `InvalidInput`; unsupported or inconsistent calculations return empty facts plus missing conditions. A caller must not convert exceptions into a seemingly valid low score. Once a valid candidate is assessed, existing high/medium/low labels remain unchanged, unknown axes stay separate, and no fourth priority category is introduced.

Snapshot hashing uses recursively typed nodes for every value, including dictionaries, numbers and Decimal values; ordinary dictionaries cannot impersonate a Decimal tag. The result contains a snapshot hash, relation, provenance IDs and, when fully verified, a condition group with constituent facts and source quotation. That view does not replace the complete original rule/timing snapshot, which the caller must retain, including applicability and source details. A hash alone is not the original conditions.

Exact arithmetic scope: measurement/threshold inputs must be finite nonnegative numbers no greater than 1,000,000,000,000 and use no more than six stored fractional decimal places. Values outside those limits are withheld, never rounded into the supported domain. All bridge arithmetic runs with private Decimal precision 40, independent of caller context; accepted operands need at most 20 significant digits for these checks. Native scoring-boundary equality is checked separately.


## Verified condition display extension

The bridge now validates complete AND constituent arithmetic and exposes a frozen `TimingConditionGroup`, while still emitting no AND scoring facts. `timing_condition_payload` serializes this group for the isolated read-only view. Calendar-only AND uses the latest independently verified constituent date as a factual all-conditions threshold date; mixed metric groups have no inferred calendar crossing date. Calendar-month duration/countdown values are explicit days, not a newly adopted 90% ratio. Scope/event/date and snapshot identity travel with the payload. `scoring_input_emitted` describes fact emission only, not final score use. The subsequent synthetic HTTP/UI connection is described in `priority-condition-preview-api.md`; ordinary runtime integration remains disabled. See `priority-calendar-and-expression.md` for the precise arithmetic boundary.
