# 任意の原事実確認から共通優先度への接続

## 既存操作との関係

既存のカルテ分析詳細にある任意の根拠確認で、利用者が元観測を選び、表示された原文と確認命題を照合する。点数の入力、必須の追加作業、運行可否の自動判断は追加しない。確認しない場合は、保存済み区分と既知の通常根拠だけを表示する。確認の保留理由は点数・高中低の区分とは別に説明し、新しい優先度区分にはしない。

S25は日常点検の原回答、同じ指摘の整備・再確認の操作履歴から候補を提示する。新しい指摘番号、同じ単語、自由文中の「再発」「悪化」だけでは成立しない。

- 再発: 別の現在観測と、修理後の異常なし再確認で解消した比較元の指摘を選ぶ。同じ具体的な症状・位置で、解消確認後の別観測で再発したことを明示確認する。
- 悪化: 前後の別観測を選ぶ。同じ症状・位置・方法・条件で比較した実際の悪化を確認する。未解消の継続や経過時間だけでは成立しない。
- 運行不可の履歴が対象原記録に含まれる場合は、この比較を既存指示の解除や部品原因へ転用しない。元の指示を確認する説明を表示する。

元事象、会社・車両、対象項目と様式の版、原回答、原担当者の安定識別、整備と再確認の前後のJSON・版・日時をサーバーで再照合する。比較元の修理・再確認原文と、現在の原観測は区別して表示する。

## 同日内の順序

承認済みのS25点数・閾値は変更しない。従来の別日の日付比較は維持する。Fact.comparison_order_verifiedは既定Falseであり、同日である場合だけ、検証済みproviderがTrueを構成できる。クライアントの裸boolは受け取らない。

同日では、新規原回答が持つオフセット付き報告日時と、元再確認の実施日時・タイムゾーンで厳密な前後順を確認し、さらに利用者による固定の比較関係命題を必要とする。日付だけの再確認、旧報告の時差不明、逆順、未来日、元版変更は通さない。旧記録へ時刻を自動補完しない。入力中の同じ日常点検で整備・異常なし確認後に別の観測を登録する既存操作を、通常HTTPで試験する。承認済み回答を変更できるようにはしない。

## 算定と保存契約

固定命題を全て確認した既存監査イベントに、原資料・原観測、本人、日時、版、fingerprintを保存する。S25はその確認が現在も再検証可能な場合のみ適用する。厳密な標準制動項目では、独立に成立する既存I40と合わせて65。その他の部位ではIやTのゼロ・安全性を補わず、確認されたS25だけを使う。

3条件の共通adapterは、新たな通常生成時だけ confirmation:<event ID>:<fingerprint> 参照と元の保存proofを付ける。既存提案のID/revisionや保存JSONを書き換えたり、現在の確認を過去提案へ自動付与したりしない。モデルはサーバーが提示した対象・出典しか選べず、24文字の決定論的表示対象も一致検証する。全文対象と原根拠は詳細に残す。確認の既知区分は新生成時の保存下限とし、後日再検証できないことを理由に低へ落とさない。

- 原本・観測・版・適用日の不一致: 保存区分を無点数で保持し、再確認が必要な理由を別に表示する。
- 明示取消: その確認参照を使った提案だけ抑止する。元の未解消指摘、別提案、通知の既読、運行判断は変更しない。
- 真正な同一指摘の修理後の異常なし再確認: 当該比較確認提案を抑止する。最終statusだけ、操作履歴欠落、別部位の修理では抑止しない。
- 法的期限の確認で期限未到来: 新しい低0を作らず、新規算定を出さない。当日の適用確認が翌日失効した場合も保存区分を無点数で保持する。

源の状態・確認・取消は分析の重要fingerprintに含める。古い提案への回答は既存の409経路で拒否し、後続の通常生成で新しいproof/revisionを使う。定期点検の生成・表示も同じproofと共通projectionを使う。通知との関連表示は元の事象参照が一致するものだけで、全車両の法的期限を個別部品通知へ転用しない。

## 検証と運用前確認

試験は隔離した合成の会社・車両・原記録だけを使用する。実利用者の記録、個人情報、実原本は公開fixtureに転記しない。全体回帰・実ブラウザの最終確認は統合候補で実施する。専門家による点数・公開基準との関係の確認は本格運用前にまとめて行い、開発の停止条件にはしない。
