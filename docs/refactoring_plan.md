# レップの指摘と全体構造の対応

会議の「app.pyへの機能集中」「目的ごとの分割」「UI・出力・設計思想の継承」
に対し、個別の関数抽出から、アプリ全体の起動・DB・登録・処理の境界を
組み替える改修へ進めた。現在の構成・起動手順・検証結果は
[application_architecture.md](application_architecture.md) を参照。

| 指摘 | 対応 | 残る検証 |
| --- | --- | --- |
| app.pyの集中、目的ごとの管理 | 全業務領域を責務別モジュールへ配置。factory、extensions、models、routes、databaseを分離 | 長い個別業務フローの設計改善は依然必要 |
| UI・出力・設計思想の継承 | テンプレート・CSS・JSを変更せず、URL・モデル・フックの契約を固定 | 実運用画面での確認 |
| 内部処理の棚卸し・軽量化 | 静的棚卸しをパッケージへ拡張。既存の重複SQL削減・日付変換改善を維持 | OCR・AI・待ち行列・本番同時負荷の実測 |
| 小さな修正もPRレビュー | 回帰CI・契約テストを保持し、全体変更を一つのPRで確認可能にする | 人による設計・運用レビュー |
| セキュリティと負荷 | 会社境界・認可・同時更新等の既存回帰テストを維持 | 認証済み動的検証、実際の同時利用条件の合意と負荷試験 |
| ER図・定義の共有 | 全57テーブルのモデル定義・索引を変更前と比較できる契約を保存 | 本番スキーマとの照合、tblsによる更新運用 |

完了の判定はファイル数やapp.pyの行数ではなく、起動でDBを書き換えないこと、
依存先を明示できること、アプリ間で状態が混ざらないこと、既存の業務契約を
保てることで行う。構造改善と性能・セキュリティの検証はそれぞれ根拠を記録する。
