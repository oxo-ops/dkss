# 共用Push 409再購読の非本番候補

## 今回の優先範囲

#398の「利用者交代で旧endpointが409になる」後続導線を、実機なしで検証できる範囲で作る。既存本番通知は維持する。TESTINGかつSHARED_PUSH_CANDIDATE時だけ専用controllerを読み込み、通常ページに候補スクリプト・actor属性を載せない。通常の登録コードは従来通り。

## 動作

- 通知許可済みの端末のみ。許可ダイアログを自動要求しない。
- Web Locksで同一origin内の候補登録を直列化。対応しない環境は購読変更前に停止する。
- 描画時の本人識別と現在の本人を照合し、古いA画面からBとして登録しない。
- セッション単位の相関値は目的分離HMAC。ログインtoken自体は返さず、この値単独では認証・権限を与えない。context応答はno-store。
- 既存購読の409のみ、本人・セッションを再確認後にブラウザ側購読解除、新endpoint作成、1回だけ保存を試みる。他人のサーバー購読は削除も引継ぎもしない。
- 401/403/500、失効、本人交代、解除失敗、同endpoint再発行は停止。1回のcontroller呼出内に無限再試行なし。ページ再読込は別呼出なので再試行し得る。サーバーも相関値を照合するため、登録直前にCookieが入れ替わっても旧相関値でBの購読を保存しない。

## 残る制約

- Web Locksは候補登録同士を直列化するだけで、logout・別の認証処理とは原子的ではない。確認直後の本人交代や権限変更により、ローカル解除だけ済んで新規登録が停止する場合は残る。通知設定の可用性を完全保証しない。
- 旧配送済み通知・OS通知欄の撤回はしない。#398の汎用payload・送信失効判定を利用するが、従来payloadの移行安全性は別。
- Web Locks未対応、購読更新にuser gestureが必要、購読解除後に同endpointが返る端末では安全側で停止。実機ごとの対応性と操作案内・手動再試行ボタンは未受入。
- 「設定できた」または利用者向け復旧完了とは扱わない。実タブレット、実SW、OS通知、通知クリック、複数タブの実動作、表示文言の現場評価は未実施。

## 検証

- JS fake PushManager/transport：13件成功。409の1回限定、session交代前後停止、endpoint再利用拒否、同時2ページ直列化、通常時購読維持を確認。
- Python関連78件成功（既存PG限定1skip）。実Flask相関値欠落/旧値拒否、新値で登録成功、候補のみscript表示を追加。
- CI用PG18 workflowにJS試験も登録。今回差分のCIは未実行。
- 実通知送信、Render設定変更、DB変更、デプロイなし。

独立レビュー：JS13件・Python18件成功、非本番候補として追加ブロッカーなし。指摘に従いA→B試験をBの最新相関値へ更新したうえで旧endpoint所有権409を直接検証する形へ修正。
