# 動画機能と通常導線の固定受入範囲

## 対象と基準

ユーザー指定の「動画で示した操作・画面」と、承認済み優先度計算の実データ・通常画面への接続を対象とする。仕様書にある周辺改善を追加選定しない。動画の6画面（仕様書v10 §07、K59–K64）に、ユーザー指定の入口・出口を加えた次の8行を作業範囲とする。

統合元は #373（ダッシュボード）、#374（同型式比較・交換後距離）、#376（通常入力からの共通優先度）。三PR統合起点のcheckpointは `6ff966be02d66a7946f7b0bb4576cdf9d5f9852b`、treeは `0fd31c4af0c346b0dd8422f40caf4bec56cbd139`。ローカル検証commit `89964fa47b1211bb625dc1a02f57678f6383c445` と完全tree一致。元PRの試験は引き継ぐが、元PR単独の合格を統合後の全体合格とはしない。

## 優先度の保持条件と任意の事実確認

- 承認済みのI40/T35/S25、高60以上・中25以上、T35/25/10/0/nullを変更しない。高・中・低の第4区分は追加しない。欠損を0や低へ推測しない。優先度は確認・対応の順序であり、運行可否は人が判断する。
- 再発・悪化S25は、比較元と現在の原観測を選び、同じ症状・位置と、修理・異常なし確認後の再発または同条件比較での悪化を任意に確認する。原事象と日時・担当者・版の連鎖が必要。新ID・コメント変更・時間経過だけを再発や悪化にしない。同日順序は新規のoffset付き元時刻と明示確認で検証し、日付だけの旧記録へ時刻を補わない。
- メーカー即時条件は、実車観測と原本checksum・引用範囲を結び、現車であること、対象への適用、発動条件の成立、条件下の即時要求をそれぞれ確認する。非周期の原本通達も扱う。周期基準の数値や一般警告だけを即時要求に変換しない。
- 車検の法的期限は、同一車両の原本記載満了日、最新の更新・訂正、公示延長・例外等を確認した当日の適用根拠に限定する。満了前は新しい低や0を付けず、満了日当日/超過時だけ承認済み下限へ渡す。翌日は確認保留とし、日付末の失効時刻や運行可否は判断しない。詳細は[車検証の適用確認](../priority-certificate-confirmation.md)。
- 任意確認は既存カルテ分析内の独立formで、点数入力や通常点検・取込の新必須作業ではない。選択→原文preview→明示確認の順とし、previewだけでは保存しない。既存ChecklistEventの専用種別に当時の本人・権限・日時・元版・確認命題を追記する。取消・訂正は旧履歴を残し、点検解消・通知完了・運行許可として扱わない。
- 保存は生成を直接起動しない。既存の自動分析workerが変更fingerprintを巡回で検知し、重要入力変更として通常queueへ予約する（通常は検知から2分後。worker稼働・処理待ち・エラーによる遅延は別）。同じ分析画面の状態表示と提案欄は60秒ごとのGETで更新する。手動再分析ボタンや新しい自動生成は追加しない。正常な新規生成のサーバー最終処理で、根拠の成立する確認済み条件をAIの採否にかかわらず補完する。同じ元観測の明示refが一致する候補はまとめ、異なる事象を対象名だけで同一視しない。上位5件は概要の表示上限であり、残りは分析画面へ進んで確認できる。生成前・生成失敗時に新しい点数を確定した表示にはせず、元の保存結果と根拠確認履歴を保持する。
- 確認/取消は重要入力fingerprintを変え、旧表示への回答を409で拒否する。新生成時のproofと現在の原本が一致する提案だけへ新条件を適用し、旧提案へ後から事実を結び直さない。明示取消・真正な異常なし解消は当該確認提案だけを外し、原本変更・適用日変更等は保存区分を無点数で保持する。
- 通知は、同会社・現行認証・通知所有者・未削除車両の既存閲覧境界に加え、運行判断event/元judgment fingerprintまたは再確認defect/登録日時/元回答が一致する保存提案にだけ関連付ける。専用の人の停止指示60と登録上の再確認待ち25を、一覧・詳細・最近の通知で同一提案ID/版へ関連表示する。全通知や車両全体の高を別部品へ広げず、任意確認の3条件を新しい通知として発行もしない。異会社・失効identity・古いevent・曖昧な同時刻・元proof欠損では関連を作らない。通知本文・発行・既読・ソート・人の運行判断は変更しない。
- 定期AI提案は、新規の通常生成時にserver側の元source proofを保存し、通常GETへ共通点数・順序・根拠・提案件数集計を接続した。既存proofなし保存提案は元区分を無点数で保持し、自動backfillやGET再生成を行わない。集計対象は提案であり、通知既読数・故障率・安全状態の集計ではない。
- AND時期の到達前の接近度、暦月90%の解釈は未定義。AND全条件到達35と、確定している暦月期限到達35/30日以内25を越えるルールを追加しない。詳細は[採用済みメーカー時期基準](../priority/adopted-timing-stage2-20261111.md)。
- 未接続理由は具体的な根拠不足として残す。新しい入力欄や利用者の追加手作業を架空に要求しない。専門家確認は本格運用前にまとめ、実装・隔離検証を止める条件にしない。

## 検証の区別と最終回帰

三PR統合の影響範囲試験と隔離HTTP preflightに加え、同じ候補の連続受入で点検通知・人の判断・再確認、複数提案の順序/旧版回答拒否、請求書確認・訂正・再送・後着を確認した。費用・比較母数・交換後距離は通常HTMLと原記録を照合し、通常queue/jobが訂正後の入力と原本SHA付きsource/fingerprintを保存することも確認した。合成モデル応答は提案なしであり、請求書からの優先度やモデル品質の合格ではない。

通知の専用境界試験はHTMLエスケープ・固定URL・同一event/元回答・所有者/認証・欠損・保存不変を確認した。定期の専用試験は通常入力50、人の停止60、登録済み再確認待ち25、原本付き採用時期35と元proof保存/旧JSON保持、共通表示と提案件数を確認した。

統合browser harnessは既存のnormal/instruction/recheck/invoiceに通知関連導線とperiodic_instruction/periodic_timingを追加し、既存CI環境を再利用する。任意確認の新ケースは選択/preview/保存/訂正取消・二重送信/古い版・狭幅・非nested formを合成DBで確認するため追加済み。新ケースの2つの明示POSTだけを許可し、既存GET-onlyケースの制限を緩めない。既存ケースは実fixture POST後、ブラウザにsame-origin GETだけを許し、通知→提案→元点検、履歴→同一整備→原本、概要→分析、定期の根拠展開・一覧/戻るを確認する設計である。既存の点検・整備・請求書フォーム入力/送信と未読の自動既読POSTは対象外。任意確認formだけは新ケースで実操作を検証する。実Chromiumの描画・操作は未実行で、HTTP preflightを描画合格としない。既存Flask fixtureはCSRF無効の合成セッションで、追加任意確認browserはCSRFを有効にして実tokenを送信する設計。合成OCR/分類/AI文言を使い、実ログイン・外部配信・OCR/モデル品質の合格は主張しない。

最終候補が揃った段階で、必要な実ブラウザ受入と全体回帰をまとめて実行する。小修正ごとに全体試験・承認・デプロイを繰り返さない。

#376の[全体回帰43003903893](https://github.com/oxo-ops/dkss/actions/runs/43003903893)は、2001件のテスト開始行を出力した後、15分上限でcancelledとなった。失敗outcomeは記録されていないが、最終summaryと後続JSには到達しておらず、全体合格とは扱わない。この単独候補の再実行はしない。

最終統合候補1回の全体回帰に余裕を持たせるため、既存regression jobの上限を15分から**有限の30分**へ変更する。変更は `timeout-minutes` のみ。試験内容・順序・スキップ条件・安全ガード・読取専用GitHub権限・exact-head照合は変更しない。本変更時点では全体回帰を再実行しない。製品機能・本番設定の変更ではなく、実行時間を踏まえた検証枠の調整である。

試験は架空データと使い捨てDBを使う。本番アクセス、実AI・外部配信、マージ、配備、既存DB再初期化、復旧、運用設定変更はこの受入に含めない。
