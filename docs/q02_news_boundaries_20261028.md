# Q02 ITCのお知らせと通知先と添付の境界

## 対象と選定

候補検索APIの検証に続き、選択後のお知らせ作成・編集・削除を実Flask要求で検証する。
対象は `/itc/news/new`、`/itc/news/<id>/edit`、`/itc/news/<id>/delete`。
通知レコードの本人操作や添付の取得は既存Q02で検証しているが、お知らせの書込と宛先の展開、削除時の添付処理は直接検証していなかった。
アプリ本体、Q04のマスタ変更・並列更新、Q07の請求書費用レビューには変更を加えない。

## 追加7件

| 条件 | 期待結果 |
| --- | --- |
| ITCが全員・会社・管理者・営業所・個人向けに登録し、会社・操作者を偽装 | 現在会社の対象利用者だけに通知を作る。外部通知の呼出先も同会社。監査は実操作者 |
| 他社だけにある会社コード・営業所名・利用者名を新規と編集へ送信 | 403で拒否。添付保存と外部通知の呼出しなし。DB・一時添付を変更しない |
| 別会社の同名ITC利用者が元会社のお知らせIDを指定 | 自社の編集画面は開ける。他社の画面・編集・削除は戻され、DBと添付を変更しない |
| 入力画面を開いた後にITCから管理者へ降格して旧Cookieを再送 | 新規・編集・削除を拒否。外部通知と添付削除なし |
| 入力画面を開いた後にロックしてURLごとに旧Cookieを戻す | 新規・編集・削除はログインへ戻る。DBと添付は不変 |
| 自社のお知らせを編集してから削除 | 自社の変更と監査、未参照添付の削除は成功。他社の同名ファイルとDBは保持 |
| CSRF有効で欠落・別セッショントークンを新規・編集・削除へ送る | 400でデータ・添付は不変。現セッションの正規トークンでは削除可 |

業務DBはNews・Notification・AuditLogの全列、一時添付は両社の全ファイル内容を比較する。
通知作成は実際のDB処理を通し、外部送信のdispatchだけを模擬して呼出先の会社・利用者を確認する。
旧Cookieを再設定して、最初の拒否によるログアウトに後続試験が依存しないようにする。
ITCの会社停止時の扱い、編集後の既存通知の更新方針、同一会社内で複数のお知らせが添付を共有する場合の削除方針は今回判定しない。


クラス名指定でimportした既存TestCaseの重複収集を防ぐ。追加7件単独はmain b9be875を基に4.527秒で成功。
配布時点では利用者PC・PR・マージ後CIは未確認。アプリ本体の変更なし。

実Flask・一時SQLite・ローカルの架空添付での検証。外部メールとWeb Pushは模擬し、実配信・S3・実ブラウザ・PostgreSQLは対象外。
