# 点検計画 API の読込軽量化（未公開候補）

## 観測
- 公開 c35ccb1f の管理者向け計画 HTML は通知更新の before_request を通る。データ変更なし条件のため、公開画面の反復 GET・負荷試験は行っていない。
- 既存 Render の計画パス別 HTTP 指標は空で、実利用の待ち時間は未確定。
- 直近の粗い資源指標では 0.5 CPU / 512 MiB、メモリ約 244–316 MiB。平均値でありピーク余裕の保証ではない。
- 隔離した架空 160 台・過去 9,600 件で、全履歴を車両×種別ごとに再走査する candidate_rows が主な CPU 消費と判明。

## 変更
リクエスト内で ID と車両・種別ごとの索引を一度作る。履歴順序、基準日、種別判定、認可・会社境界、原本リンク、出力内容、データ更新は変更しない。永続キャッシュや古い結果の再利用は行わない。

## 検証
- ローカルの実 API 3 回ずつ、プロファイラなし中央値 1512.38 ms → 278.58 ms（81.6% 短縮）。合成 fixture に限る観測で Live の改善率ではない。
- JSON 全体 SHA256、件数 800、出力バイト数、SQL 16 回、書込み 0 は前後一致。
- 点検計画・Excel・会社境界・請求書実績・通知関連の既存 177 テスト成功。
- 専用 CI は固定 baseline と候補を同じ runner で比較する。正しさは JSON/件数/SQL/書込み一致で判定し、経過時間は観測として記録。
- UI/JS/CSS に変更なし。#500 の計画 UI と製品ファイル競合なし。統合後の実ページ検査が別途必要。

## 残る調査
管理者の HTML 前処理で走る通知更新・DB ロック待ち、旧記録の種別根拠取得、ブラウザでの年間一覧 DOM 生成は別の遅延要因になり得る。今回の索引化で全部解消したとは扱わない。実 iPhone・Live API の実測は未確認。
