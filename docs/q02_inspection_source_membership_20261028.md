# Q02 点検記録IDから取得する原本の車両境界（2026-10-28）

基準: main `6d7d8c9ccc7bd661cd86a6b5fa68b99da2a7c668`。

## 再現した問題

`GET /vehicle/periodic-inspections/<record_id>/source` は点検記録と取込資料の会社・完了状態を確認する一方、現在の車両の会社と、原本の取込結果に記録された車両との紐付けを確認していなかった。
カルテ経由の `/vehicle/karte/<vehicle_id>/documents/<draft_id>/source` では拒否される紐付け不一致でも、点検記録IDから直接要求するとPDFが返る。

修正前の実Flask試験で、車両の会社変更、点検記録の他社車両への付替え、取込結果の車両不一致、不正なrecords構造の4ケースすべてが200となることを再現した。

## 修正

点検原本の入口で、点検記録の会社に現在の車両が存在することと、完了した原本のresult_jsonのrecords配列にその車両が含まれることを再確認する。不一致や不正構造はPDFを返す前に404。
既存の原本配信処理と、PDF・画像・画像のPDFプレビュー変換、no-store/nosniffのヘッダーは維持する。
車両の削除状態やハッシュ検証の仕様は変更しない。運転日報の原本経路も変更しない。

## 試験

`tests/test_q02_import_document_boundaries.py` に5件追加。

- 管理者・同社の一般利用者は正常な点検原本を取得でき、カルテ経由と同じ本文・安全ヘッダーである。
- 上記4種類の不一致は404で、PDFとダウンロードヘッダーを返さない。
- 各要求後に車両・取込資料・点検記録の全列が変わらない。

既存の資料境界10件は再作成せず、新規5件とあわせて15件。外部AIは模擬し、アップロードと確定は実Flask・一時SQLiteで実行する。修正前は15件中4件失敗、他11件成功。
修正後の資料境界15件と既存取込フロー52件は合計67件、35.389秒で成功。
