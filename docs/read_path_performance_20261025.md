# 読取り処理の性能計測と最初の改善

基準: PR #151 / commit `2d34d123519d30602ab134fc3e6027f14393b9cf`。
レップの「重い処理を棚卸しし、分割・軽量化する」という指摘への第2段階。

## 確認した原因

- 車両概要の1表示でSQLが50回発行され、整備記録6回・定期点検記録8回・
  日常点検結果5回など、同じ会社／車両の記録を複数の集計関数が再取得していた。
- 分析結果APIの処理時間は、同型式・同初度登録年の比較車両数とともに増えた。
  200台のプロファイルでは比較集計が主要な時間を占め、
  分析集計200回と、strptimeの日付変換18,074回を確認した。
- SQL件数だけでは分からないPythonの繰り返し処理がある。
  DBやサーバーの増強だけで解決することは前提にしない。

## 今回の変更

### 概要の描画内で読取りを共有

`VehicleReadSnapshot`を1回の概要構築ごとに作り、
整備・日常点検・定期点検等の生データを同じ描画内で再利用する。
履歴、部品集計、未解決指摘に明示的に渡す。
各取得でcompany_codeとvehicle_record_idを指定し、
異なるスコープの関数へ渡した場合は取得前に拒否する。

アプリ全体やセッションに残すキャッシュではない。
次の構築ではDBを読み直し、更新を反映する。
DBのトランザクション分離レベルを変更したり、
複数テーブルを同時点のデータに固定する機能ではない。

### 分析の日付変換を共通化・軽量化

保存済みの標準日付YYYY-MM-DDをdate.fromisoformatで処理する。
従来対応していた桁の省略等はstrptimeへ回す。
走行距離の根拠判定で使う空白除去・スラッシュ置換も従来通り。
分析対象や根拠を削らず、AIの入力・判定条件も変えない。

## 同一データでの交互比較

一時SQLiteに、1台・50台・200台の合成データを作成。
各車両に整備12件・運行12件・日常点検30件を登録した。
200台では整備2,400件・運行2,400件・日常点検6,000件。
200人同時接続の試験ではない。

同一データ・同一プロセスで、従来の日付変換と共有読取り無効の「変更前相当」、
および今回の処理を交互に実行した。
各条件の最初の1回を除外し、後続7回の中央値を比較した。
実行順も交互に反転し、順序の偏りを抑えた。
共有実行環境のため、経過時間にはCPUの割当て等によるばらつきがある。

### 200台時の結果

| 対象 | 変更前相当の中央値 | 変更後の中央値 | SQL件数 |
| --- | ---: | ---: | --- |
| ダッシュボード | 38.952ms | 41.492ms | 27〜28 → 27 |
| 車両概要 | 73.990ms | 64.750ms | 50 → 45 |
| 分析結果API | 685.110ms | 323.476ms | 21 → 21 |
| 通知未読件数 | 15.839ms | 15.798ms | 13 → 13 |

概要のSQL削減は各7回で同じ件数を確認した。
ダッシュボードと通知処理は今回改修しておらず、高速化を主張しない。
ダッシュボードのSQL件数には利用者情報更新等による1件の変動がある。
分析結果APIの変更前相当は461.672〜738.439ms、
変更後は307.366〜574.387ms。中央値だけを応答時間保証に使わない。

### 分析結果APIの台数別中央値

| 合成車両数 | 変更前相当 | 変更後 |
| --- | ---: | ---: |
| 1台 | 19.199ms | 15.177ms |
| 50台 | 84.562ms | 61.232ms |
| 200台 | 685.110ms | 323.476ms |

詳細は`read_path_performance_20261025.json`。

## 検証

- 全281件の回帰テスト成功。
- 追加7件: 概要の出力一致・重複SQL削減、次回構築時の更新反映、
  会社／車両スコープ違いの拒否、他社行の除外と取得の再利用、
  分析入力・出典・fingerprint一致、従来の日付形式、閏年をまたぐ日付変換。
- 既存の概要・費用・点検・整備・取込・分析のテストを含めて実行。
- 本番のデータ、APIキー、DB設定、アップロード済みファイルを使用していない。
  計測時にAIとソケット接続を監視・禁止し、外部呼出し0件を確認した。
- URL、テンプレート、CSS、JavaScript、DBモデル定義は今回変更していない。

## 次に残ること

分析の比較集計自体はまだ台数に比例して増える。
VehicleAnalysisServiceへの責務分離、集計データの取得・計算の見直し、
概要以外の重複SQL、通知の確認頻度・ロック、原本一覧の全件読取り等は後続。
分析のAI推論時間・トークン数は今回未計測。
PostgreSQL、Render、実データ、同時接続、実際のブラウザ転送・描画、
動的セキュリティ、復旧の試験も未実施。
