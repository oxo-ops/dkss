# 車両分析の入力・予約・実行・保存の分離

基準: 性能改善PR #152 / `afd34705ee6fa4808dfe25fa1b3d1eddc5a3a4de`。
レップの「処理を目的ごとに分け、クラスで管理する」という指摘への対応。
適用順序は #151 → #152 → 今回。

## 変更した範囲

app.pyにあった分析入力の組立て、予約の判定、ジョブ実行の進行を
サービスクラスへ切り出した。DBへの問い合わせ・更新はrepositoryへ分離した。
app.pyの対象3関数は計400行から35行となり、関連importが5行増える。
既存の関数名・引数は維持し、既存CLI・ローカルワーカーから呼び出せる。

| クラス | 責務 | 明示的に渡す依存 |
| --- | --- | --- |
| VehicleAnalysisInputService | 分析期間、登録データ、比較条件、分析入力の組立てを進める | 入力repository、集計・比較・payloadの関数、日付、設定読取り |
| VehicleAnalysisQueueService | 重要変更・日次変更・既存予約・実行中の状態に応じて予約を判定 | ジョブrepository、UTC時刻、保存結果のJSON読取り |
| VehicleAnalysisJobService | 実行権取得、入力取得、AI／記録確認、保存、失敗処理を進める | ジョブrepository、入力読取り、AIクライアント、時刻、トークン生成、入力のcontext、logger、キー読取り |
| VehicleAnalysisInputRepository | 車両に属する整備・運行・部品・不具合・定期点検を取得 | 必要な5種類のモデル |
| VehicleAnalysisJobRepository | 状態取得、条件付き実行権取得、延長、保存、再試行状態更新 | DB、分析状態モデル、車両モデル |
| AnalysisComparisonSettings | 自動分析の比較設定の読取り・検証 | 設定のmapping |

サービスのモジュールはFlask・app.py・SQLAlchemyをimportしない。
repositoryもapp.pyをimportせず、必要なモデルとDBだけを受け取る。
globals()やアプリの名前空間全体を渡す方法は使用していない。
各アプリ関数を呼ぶ時点で依存を渡すため、テストの時刻・AI・入力の差替えを維持する。

## 維持した動作

- 分析期間は日本時間の当日から2年前。閏日は存在する日付に調整する。
- 会社・車両で入力を限定し、部品は子と整備親の双方の所属を検証する。
- 運行実績は基準日以前のものだけを入力に含める。
- 初回・重要な変更は2分後、日次変更は次の日本時間03:00に予約する。
- 先に予約されていた時刻を遅らせない。同じ入力の再試行時刻を上書きしない。
- 実行中の予約変更は実行権のトークンを保持する。
- 実行権は入力ハッシュ・状態・実行予定時刻・期限を条件に取得する。
- AI実行中の進捗callbackで実行権を3分延長する。
- 重要履歴がない場合はAIを呼ばず、記録確認結果を保存する。
- 入力変更が実行と重なった場合は結果を保存し、新しい入力ハッシュと再予約を保持する。
- 保存時とエラー記録時も自分のトークンで対象を限定し、別の所有者を上書きしない。
- 失敗した場合は既存結果を保持し、キーを伏せた最大500文字のエラーと1時間後の再試行を記録する。
- 分析入力、出典、比較条件、fingerprint、保存結果のキー・時刻形式を維持する。

## トランザクションの境界

| 操作 | 境界 |
| --- | --- |
| 入力取得 | 読取りのみ |
| 予約 | 新規状態の作成は従来同様savepointを使用。外側のcommitは呼出元が担当 |
| 実行権取得 | 条件付きUPDATE後にcommit |
| 実行権延長 | 所有権が有効ならcommit。失っていたらrollbackして中止 |
| 結果保存 | expire_all後にトークン一致の行をwith_for_updateで再取得し、更新してcommit |
| 失敗処理 | rollback後、自分のトークンの行だけ更新してcommit |

今回、予約間隔・再試行間隔・ロック条件・DBモデル・索引・列を変更していない。

## 検証

全301件の回帰テストが成功した。
既存テストに20件を追加して、入力期間・設定、予約・実行・保存の条件を確認する。
実行権の変更や入力の変更をAI callback内で割り込ませ、
新しい所有者や新しい予約が古い結果で上書きされないことを確認した。
これはSQLite上の順序制御であり、PostgreSQLでの複数プロセス同時実行試験ではない。

旧3関数を基準コミットから取り出し、同じ一時DB・固定時刻・モックAIで比較した。
入力・出典・fingerprintの一致、およびAI完了／記録確認／エラー、
初回予約／日次変更／実行中変更の各保存フィールドの一致を確認した。
本番のDB・原本・外部AIは使用していない。

## 残っていること

集計・型式比較・整備知識の適用・根拠組立て自体の関数はapp.pyに残る。
今回のInputServiceには、その既存の処理をcallbackとして明示的に渡している。
これらの内部ロジック、CLIでの全社対象抽出、APIレスポンス、DBモデルや起動処理は
今回の切出しには含めていない。

本番PostgreSQLのロック、同時実行、Render上のワーカー運用、実際のAI呼出し、
負荷試験、総合セキュリティ、復旧の検証も引き続き必要。
今回のクラス分離による高速化は主張しない。
