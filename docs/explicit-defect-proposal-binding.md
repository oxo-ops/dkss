# 記録と提案の明示的な対応付け

## 非本番の最小接続

`vehicle_priority_binding.build_bound_defect_projection` は、既存の故障・不具合記録と保存済み提案の対応を、信頼できる呼出し元が明示した場合だけ、既存の共通算定へ渡す純粋な接続部である。純粋関数自体はDB、HTTP、AI、通知、時計、保存処理を呼ばない。隔離用 `read_bound_registered_defect_priorities` は既存のテスト環境限定ガードの下で実際のORM列を読取り、この関数へ渡す。既存の画面やプレビュー登録には自動接続しない。

入力は、会社・車両・取得日を固定した `DefectSnapshot`、元の提案IDと版を付けた保存内容、出典辞書、および `DefectBindingSet` とする。呼出し元は、AIによる引用や部品名一致を、そのまま対応確認済みとは扱わない。確認済みの対応だけ `correspondence_verified=True` として明示する。これを外部要求JSONから直接生成する入口は設けていない。

## 変更・曖昧さを拒否する条件

- 保存分析、出典辞書、実記録取得値の3つのfingerprintが対応付け時点と一致すること。
- 会社、車両、取得日、提案ID、提案版、対象名が完全に一致すること。
- 選んだ記録IDが元の提案の出典と出典辞書の両方に存在すること。
- DB読取後の値も対応付け時点のfingerprintと一致すること。別接続の変更があれば古い対応を再利用しない。
- 全提案へ明示的な対応があること。最初の接続では提案1件に記録1件、同じ記録の複数提案への流用を認めない。
- 登録状態が修理完了の記録は、日時矛盾の有無にかかわらず提案へ接続しない。日時矛盾は記録側の照合事項として残し、未対応提案へ復活させない。
- 以前の試算結果を、新しい原提案や版計算の入力にしない。

違反時は、表示に使える試算を作らず `InvalidInput` とする。足りない対応を低優先度へ置き換えるフォールバックはない。

## 算定と保全

正しい明示対応を通過しても、使うのは前段の登録状態から根拠を得られる点だけである。影響度、期限、再発、診断内容は推測しない。状態不明は既存算定の根拠不足として別記し、新しい優先度区分を作らない。

元の優先度、リスク欄、提案の順序、ID、版、回答、評価、出典は変更しない。試算と試算用並び順だけをコピーに追加する。入力が実車の最新状態であるとは認定しない。実記録IDを事象IDとして保持し、異なる不具合を同じ部品名だけで統合しない。

## 残る接続

通常経路での対応取得・更新方法、複数記録が1提案へ関連する場合、同じ記録に複数提案がある場合、整備・定期点検レコードの対応は未実装である。今回のコードはそれらを推測で補わない。期限接続とは別の境界であり、両者の結果を自動的に合成して提案へ配信しない。

専門家による実例確認は本格運用前の受入にまとめ、現在の実装・合成試験の待ち条件にしない。
